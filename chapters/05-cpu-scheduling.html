CHAPTER 05

CPU 排程

CPU Scheduling

本章重點

  • 排程不會讓單一工作跑得更快，只能減少等待：scheduler 決定下一個給誰，dispatcher 負責真的換過去。
  • 評估指標：CPU utilization、throughput、turnaround time、waiting time、response time，考試最常算後三個。
  • FCFS、SJF、SRTF、Round Robin、Priority 用同一題比較最清楚；SJF / SRTF 平均等待最短但會 starvation，用 aging 解決。
  • Multilevel queue 和 MLFQ 把 ready queue 拆成好幾條，MLFQ 讓 process 依行為在 queue 之間移動。
  • 多處理器要考慮 common 或 per-core queue、load balancing、processor affinity 和 hardware threading；演算法可以用 deterministic modeling、queueing model（Little's formula）、模擬或實作來評估。

核心觀念

為什麼需要排程

大部分 process 的行為是「用一下 CPU，等一下 I/O，再用一下 CPU」，一段連續使用 CPU 的時間叫做 CPU burst。當某個 process 去等 I/O，CPU 就空出來了，這時候 scheduler（排程器）要從 ready queue 裡挑一個接手，CPU 才不會閒著。

可以想成餐廳只有一個廚師，很多桌客人點餐。廚師要決定先做哪一桌，不同的決定方式會讓客人的等待時間差很多。

Preemptive 與 Non-preemptive

Non-preemptive（不可搶占）
一個 process 拿到 CPU 後，會一直用到它自己結束或去等 I/O，別人不能中途搶走。
Preemptive（可搶占）
作業系統可以在中途把 CPU 收回來交給別人，例如有更短的工作到了，或是 time slice 用完。

什麼時候要做排程決定

  1. running → waiting（例如去等 I/O）
  2. running → ready（例如 interrupt、time slice 用完）
  3. waiting → ready（例如 I/O 完成）
  4. terminated

只在 1 和 4 做決定的是 non-preemptive，其他情況也會換人的是 preemptive。現代 OS 幾乎都是 preemptive，但它會帶來 race condition：一個 process 改資料改到一半被搶走，另一個 process 讀到不一致的資料，kernel 自己的資料結構也一樣，這是第 06 章要處理的問題。

Scheduler 與 Dispatcher

  • Scheduler：決定下一個給誰。
  • Dispatcher：執行換手的動作，包括 context switch、切回 user mode、跳到程式該繼續的位置。
  • Dispatch latency：dispatcher 停下一個 process 再啟動另一個所花的時間，越短越好。

Linux 可以用 vmstat 看每秒 context switch 的次數。

常見錯誤

waiting time 是「所有」在 ready queue 排隊的時間加總，被搶占後再回來排的時間也要算。最穩的算法是直接用 turnaround − burst，不要一段一段去加，比較不會漏。

FCFS：先來先做

First-Come, First-Served，誰先到誰先用，用一個 FIFO queue 就能實作，non-preemptive。

問題是 convoy effect（護航效應）：一個很長的工作排在前面，後面一堆短工作全部被卡住，就像超市結帳排在一台裝滿的推車後面，你只買一瓶水也要等。

SJF：最短的先做

Shortest-Job-First，每次挑 CPU burst 最短的，non-preemptive。它是為了解決 FCFS 的 convoy effect：短工作先做完離開，大家的平均等待時間就會下降。可以證明在所有 process 同時抵達時，SJF 的平均 waiting time 是最小的。

缺點有兩個：

  • 不知道 burst 多長：實際上無法事先知道下一次 CPU burst，只能用過去的 burst 預測（常用 exponential averaging）。
  • Starvation（飢餓）：長工作可能一直被插隊。

SRTF：剩下最短的先做

Shortest-Remaining-Time-First，是 SJF 的 preemptive 版本。每當有新的 process 抵達，就比較「新來的 burst」和「正在跑的剩餘時間」，新來的比較短就搶過來。它解決了 SJF 的一個問題：短工作剛好在長工作開始後才抵達，在 SJF 下還是得等長工作做完。

Round Robin：輪流做

每個 process 一次最多只能用一個 time quantum（時間片，記作 q），用完就回到 queue 尾巴重新排，preemptive。它解決的是「互動感」：不管工作多長，每個人很快就能輪到一次，response time 很短。

  • q 很大：每個 process 都在 q 內做完，等於 FCFS。
  • q 很小：輪得很快，但 context switch 次數暴增，overhead 變大。
  • 經驗法則：大約 80% 的 CPU burst 應該比 q 短。

Priority 與 Aging

每個 process 有一個優先權數字，先做優先權高的，可以是 preemptive 或 non-preemptive。SJF 其實就是「burst 越短優先權越高」的特例。

Priority scheduling 一樣會 starvation，解法是 aging（老化）：一個 process 等得越久，就慢慢提高它的優先權，最後一定輪得到。

Multilevel Queue

把 ready queue 拆成好幾條 subqueue，process 依類型被固定分到某一條，例如 foreground（互動型）和 background（批次型）。每條 queue 可以用自己的演算法（例如 foreground 用 RR、background 用 FCFS），queue 之間再排程：固定優先權（上面的 queue 空了才輪到下面，可能 starvation），或分配時間比例（例如 80% 給 foreground、20% 給 background）。缺點是 process 不能換 queue，不夠有彈性。

MLFQ：多層回饋佇列

Multilevel Feedback Queue 有好幾層 queue，上層優先權高、q 小，下層優先權低、q 大。規則大致是：

  1. 新的 process 先放最上層。
  2. 把一整個 q 用完的 process，代表它很吃 CPU，往下降一層。
  3. 在 q 用完前就主動去等 I/O 的，代表它是互動型，留在原本那層。
  4. 每隔一段時間把所有 process 拉回最上層（priority boost），避免下層 starvation。

它的厲害之處是不需要事先知道 burst 長度，而是「看你的行為」自動分類，達到類似 SJF 的效果。

典型例子有三層：

  • Q0：RR，quantum 8 ms
  • Q1：RR，quantum 16 ms
  • Q2：FCFS

新 process 都從 Q0 開始，8 ms 內沒做完就降到 Q1，在 Q1 再用完 16 ms 還沒做完就降到 Q2。所以 burst 短的 process 很快在上層做完，長的會沉到下層用 FCFS 慢慢跑。

Multiple-processor scheduling

多處理器可以是 multicore CPU、multithreaded core、NUMA 系統，也可能是不同種類的核心（heterogeneous multiprocessing）。兩種做法：

Asymmetric multiprocessing
由一顆 master CPU 負責所有系統的事（包括排程、存取 kernel 資料），其他 CPU 只跑使用者程式。只有一顆碰 kernel 資料，很簡單；但 master 會成為瓶頸。
Symmetric multiprocessing（SMP）
每顆 CPU 自己排程。可以所有 CPU 共用一條 common ready queue（容易互相接手工作，但要上鎖避免兩顆 CPU 選到同一個 process，鎖會變成瓶頸），或每顆 CPU 有自己的 per-core run queue（現代 OS 最常見，不用搶鎖、cache 比較好用，但工作量可能不平均）。

Load balancing 讓所有 CPU 的工作量平均，只有各自有 queue 的系統才需要：

  • Push migration：由一個 task 定期檢查，把忙的 CPU 上的 process 推給閒的。
  • Pull migration：閒的 CPU 主動去忙的 CPU 拉工作過來。

Processor affinity：process 在某顆 CPU 上跑過，那顆的 cache 裡都是它的資料（warm cache）；搬到別顆就要重新 cache miss、慢慢載入（cold cache）。所以 OS 會盡量讓 process 留在同一顆 CPU：

  • Soft affinity：盡量留在同一顆，但不保證。
  • Hard affinity：process 可以指定只能在哪些 CPU 上跑。
  • NUMA：還要讓 process 跑在它記憶體所在的那顆 CPU 附近。

注意 load balancing 會把 process 搬走，和 affinity 互相抵觸，要取平衡。

Hardware threading

CPU 存取記憶體時常常要等資料回來，這段時間叫 memory stall，核心其實閒著。解法是讓一個核心有兩個（或更多）hardware thread：一個在等記憶體時，馬上換另一個執行（Intel 叫 hyper-threading）。對 OS 來說，每個 hardware thread 都像一顆 logical CPU。

Coarse-grained multithreading
遇到 memory stall 這種長延遲事件才換 thread。換的時候要把 pipeline 裡做到一半的指令清掉（flush），成本高。
Fine-grained（interleaved）multithreading
在每個指令週期的邊界就切換，指令交錯著跑。需要硬體有額外的電路支援，但切換成本很小。

所以排程有兩層：OS 決定哪個軟體 thread 放到哪個 hardware thread（logical CPU）上；核心自己決定這一刻執行哪個 hardware thread。

演算法的評估

先決定目標，例如「在 response time 不超過 300 ms 的前提下，讓 CPU utilization 越高越好」，再用以下方法比較：

Deterministic modeling
拿一組固定的工作量，算出每個演算法的表現，就是我們在「實際例子」做的事。簡單快速，但結果只適用那組資料。
Queueing models
把系統看成由 CPU、I/O 裝置等 server 組成的網路，用機率分布描述到達和服務時間。最常用的是 Little's formula：n = λ × W，n 是平均排隊長度、λ 是平均到達速率、W 是平均等待時間。系統穩定時，進來的速度等於離開的速度，所以這個式子對任何排程演算法都成立。
Simulations
用程式模擬系統，輸入可以是隨機產生的分布，或從真實系統錄下來的 trace。比較準，但很花時間。
Implementation
直接實作在真的 OS 上測量，最準，但成本最高，而且使用者知道排程方式後可能改變行為。

Little's formula

某系統平均每秒有 7 個 process 抵達（λ = 7），每個 process 平均在 queue 裡等 2 秒（W = 2），那 queue 裡平均有 n = 7 × 2 = 14 個 process。反過來，如果知道平均排隊長度是 14、到達速率是 7，也能推出平均等待時間是 2 秒。

Pseudocode

SRTF 模擬

FUNCTION simulate_srtf(processes)
    time = 0
    remaining = {p: p.burst FOR p IN processes}
    finished = 0
    WHILE finished < len(processes)
        // 找出已抵達、還沒做完、剩餘時間最短的
        ready = [p FOR p IN processes IF p.arrival <= time AND remaining[p] > 0]
        IF ready is empty THEN
            time = time + 1          // CPU idle
            CONTINUE
        END IF
        p = argmin(ready, key = remaining[p])
        IF p.first_run is undefined THEN
            p.first_run = time       // 用來算 response time
        END IF
        remaining[p] = remaining[p] - 1   // 一次只跑 1 單位，才能隨時被搶
        time = time + 1
        IF remaining[p] == 0 THEN
            p.completion = time
            finished = finished + 1
        END IF
    END WHILE
END FUNCTION

Round Robin 模擬

FUNCTION simulate_rr(processes, q)
    sort processes BY arrival
    queue = empty FIFO
    time = 0
    next = 0                         // 下一個還沒進 queue 的 process
    WHILE queue not empty OR next < len(processes)
        IF queue is empty THEN
            time = max(time, processes[next].arrival)
        END IF
        // 把已經抵達的都放進 queue
        WHILE next < len(processes) AND processes[next].arrival <= time
            queue.enqueue(processes[next]); next = next + 1
        END WHILE

        p = queue.dequeue()
        run = min(q, p.remaining)
        time = time + run
        p.remaining = p.remaining - run

        // 先放執行期間新抵達的，再放剛用完 q 的 p
        WHILE next < len(processes) AND processes[next].arrival <= time
            queue.enqueue(processes[next]); next = next + 1
        END WHILE
        IF p.remaining > 0 THEN
            queue.enqueue(p)
        ELSE
            p.completion = time
        END IF
    END WHILE
END FUNCTION

優缺點

演算法可搶占優點缺點適用情境
FCFS否最簡單，公平convoy effect，平均等待時間長批次工作、burst 差不多長
SJF否同時抵達時平均 waiting 最小要預測 burst、長工作 starvation能估計工作長度的批次系統

MLFQ是不用預測 burst，自動區分互動和計算型參數多、調校複雜一般用途作業系統

自我測驗

Q1. 三個 process 都在時間 0 抵達，burst 分別是 P1 = 24、P2 = 3、P3 = 3。用 FCFS，順序 P1、P2、P3 和順序 P2、P3、P1 的平均 waiting time 各是多少？

答案：P1、P2、P3 是 (0 + 24 + 27) ÷ 3 = 17；P2、P3、P1 是 (0 + 3 + 6) ÷ 3 = 3。

原因：這就是 convoy effect。長工作排在前面時，兩個短工作都要多等 24。把短的排前面，長的那個只多等 6，整體平均大幅下降，這也是 SJF 想法的由來。

Q2. Round Robin 的 time quantum 設成無限大，會變成哪個演算法？

答案：FCFS。

原因：q 無限大代表沒有人會因為時間到被趕下來，每個 process 都會跑到自己結束或去等 I/O，而 queue 是照抵達順序排的，所以行為和 FCFS 一模一樣。

Q3. 為什麼說 SJF 在現實中「做不到」？作業系統要怎麼近似它？

答案：因為無法事先知道下一次 CPU burst 多長，只能用過去的紀錄預測。

原因：常見做法是 exponential averaging：τn+1 = α · tn + (1 − α) · τn，其中 tn 是這次實際的 burst，τn 是上次的預測，α 介於 0 和 1 之間，決定要多相信最近一次的結果。MLFQ 則是另一種思路：不預測，直接看行為分類。

Q4. 在 MLFQ 中，如果一個 process 總是在 q 用完前一點點就去做一個很短的 I/O，會發生什麼問題？

答案：它可以一直留在最高優先權的那層，霸佔 CPU。

原因：只看「有沒有用完一整個 q」的規則可以被鑽漏洞。OSTEP 的改良是改成記錄「在這一層總共用了多少 CPU 時間」，累積用完配額就降級，不管中間有沒有去做 I/O。

Q5. 為什麼 load balancing 和 processor affinity 會互相衝突？

答案：load balancing 會把 process 搬到比較閒的 CPU，但搬走就失去原本 CPU 上的 warm cache，違反 affinity 想讓它留在原地的目的。

原因：搬到新的 CPU 後 cache 是 cold 的，一開始會一直 cache miss，要從主記憶體重新載入，反而變慢。所以 OS 要權衡：只有工作量差太多時才搬，或盡量搬到共用 cache 的核心。

Q6. 一個系統的 ready queue 平均有 20 個 process，平均每秒有 5 個新 process 抵達，平均每個 process 要等多久？

答案：4 秒。

原因：用 Little's formula n = λ × W，20 = 5 × W，所以 W = 4 秒。這個關係只要系統處於穩定狀態（進來的速度等於離開的速度）就成立，和用哪種排程演算法無關。

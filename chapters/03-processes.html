OS notes

CHAPTER 03

行程

Processes

本章重點

  • program 是硬碟上的檔案，process 是正在執行中的 program；記憶體分成 text、data、heap、stack。
  • process 在 new、ready、running、waiting、terminated 之間切換；OS 用 PCB 記住每個 process，context switch 就是在存、讀 PCB。
  • long-term scheduler 決定誰能進記憶體，short-term scheduler 決定誰上 CPU，medium-term 用 swapping 調整記憶體裡的 process 數量。
  • UNIX 用 fork() 產生 child、exec() 換掉程式、wait() 回收 child，沒被回收的是 zombie，parent 先走的是 orphan。
  • cooperating process 用 IPC 溝通：shared memory 或 message passing；具體工具有 pipe、socket、RPC。

核心觀念

Program 和 Process

program（程式）是一個放在硬碟上的檔案，例如 a.out，它本身不會動。當你執行它，作業系統把它載入記憶體、分配資源、開始一行一行跑，這個「正在跑的東西」才叫做 process（行程）。

可以把 program 想成一份食譜，process 是「某個人照著食譜正在做菜」這件事。同一份食譜可以同時有三個人在做，就像同一個程式可以同時開三個 process（例如開了三個瀏覽器視窗），每個人做到第幾步、用了哪些鍋子都不一樣。

記憶體配置

一個 process 在記憶體裡大致長這樣：

  高位址  ┌────────────────┐
         │     stack      │  ← 函式呼叫、區域變數，往下長
         │       ↓        │
         │                │
         │       ↑        │
         │     heap       │  ← malloc() 動態配置，往上長
         ├────────────────┤
         │     data       │  ← 全域變數、static 變數
         ├────────────────┤
         │     text       │  ← 程式碼本身（唯讀）
  低位址  └────────────────┘
記憶技巧

stack 和 heap 從兩端往中間長，中間留空，這樣兩邊都可以彈性變大。遞迴寫太深會 stack overflow，就是 stack 長到撞牆了。

五種狀態

              ┌──────── interrupt ─────────┐
              ▼                            │
 [new] ──▶ [ready] ──── dispatch ────▶ [running] ─ exit ─▶ [terminated]
              ▲                            │
              │                            │ I/O or event wait
              │                            ▼
              └──── I/O done ──────────[waiting]
New
正在被建立，還沒準備好。
Ready
什麼都準備好了，只差 CPU，在 ready queue 排隊。
Running
正在 CPU 上執行。單核 CPU 同一時間只會有一個 process 在這個狀態。
Waiting（也叫 Blocked）
在等某件事發生，例如等硬碟讀完、等使用者輸入。這時候就算給它 CPU 也沒用。
Terminated
執行結束，等作業系統回收資源。
常見錯誤

waiting 結束後是回到 ready，不是直接回到 running。I/O 做完只代表它又可以排隊了，要不要馬上給它 CPU 是 scheduler 決定的。

PCB

作業系統要同時管很多 process，所以每個 process 都有一張「身分證」，叫做 PCB（Process Control Block）。裡面記錄：

  • process state：現在是五種狀態中的哪一種
  • program counter：下一行要執行的指令位址
  • CPU registers：暫存器的值
  • CPU 排程資訊：優先權、在哪個 queue
  • 記憶體管理資訊：page table 等
  • I/O 狀態：開了哪些檔案、用了哪些裝置
  • PID（process ID）和 parent 是誰

Context switch

CPU 要從 process A 換成 process B 時，必須先把 A 現在的狀態存進 A 的 PCB，再把 B 的 PCB 讀出來放回 CPU。這個動作叫 context switch（內容切換）。

這就像你在寫作業寫到一半要去接電話，你會先在題目旁邊做記號「寫到第 3 題第 2 步」，講完電話再照記號接著寫。記號就是 PCB，做記號和看記號的時間就是 context switch 的成本。

補充

context switch 期間 CPU 沒有在做任何使用者的工作，是純粹的 overhead。切換太頻繁，系統反而會變慢。實際花多少時間依硬體和作業系統實作而異，大約是微秒等級。

建立 process：fork() 與 exec()

在 UNIX/Linux 上，新的 process 都是由舊的 process 產生的，形成一棵 process tree。

  • fork()：把自己複製一份。呼叫一次，回傳兩次：在 parent 裡回傳 child 的 PID（大於 0），在 child 裡回傳 0，失敗回傳 -1。
  • exec() 系列：把目前 process 的記憶體內容換成另一個程式，PID 不變。
  • wait()：parent 等 child 結束，並回收 child 的資源。
常見錯誤

child 結束了但 parent 沒有呼叫 wait()，child 的 PCB 會留著，變成 zombie process。如果 parent 先結束，child 會變成 orphan process，在 Linux 上通常會被 init（或 systemd）接手。

Schedulers

Long-term scheduler（job scheduler）
決定哪些 process 可以進入記憶體、放進 ready queue（new → ready）。很久才動一次（幾秒到幾分鐘），重點是控制 degree of multiprogramming，也就是記憶體裡同時有多少個 process。
Short-term scheduler（CPU scheduler）
從 ready queue 挑下一個上 CPU 的 process（ready → running）。每幾毫秒就要做一次，所以一定要快。有些系統只有這一種 scheduler。
Medium-term scheduler（swapping）
記憶體被過量使用時，把某個 process 整個移出記憶體（swap out），之後再移回來（swap in），用來降低 degree of multiprogramming。

記憶體裡要放很多個 process，是因為只放一個的話，它一去等 I/O，CPU 就沒事做。process 分兩種：

  • I/O-bound：大部分時間在等 I/O，例如文書編輯器在等你打字。
  • CPU-bound：大部分時間在運算，例如訓練模型、影片轉檔。

兩種要混合得好：全部 I/O-bound 時 ready queue 常常是空的、CPU 閒著；全部 CPU-bound 時 I/O 裝置閒著，大家都覺得電腦很卡。

process 一輩子都在各種 queue 之間搬來搬去：ready queue 和每個裝置各自的 wait queue。queue 其實就是一串用 linked list 串起來的 PCB，換 queue 就等於換狀態。在 Linux 裡 PCB 是一個叫 task_struct 的 C struct，kernel 用 doubly linked list 串起所有 process，並用 current 指標指向正在執行的那一個。

補充

手機的多工比較受限：早期 iOS 一次只有一個 foreground app 在跑，其他全部暫停，iOS 4 之後才允許有限度的背景執行；Android 則可以用 service 在背景做事。原因是手機的記憶體、電池都比較有限。

Process termination

process 執行完最後一行會呼叫 exit()，把狀態值回傳給 parent（parent 用 wait() 拿到），OS 回收它的資源。parent 也可以用 abort() 終止 child，例如 child 用了超過分配的資源、工作已經不需要，或 parent 自己要結束。有些系統不允許 child 在 parent 結束後繼續存在，parent 一結束就把所有子孫一起終止，叫 cascading termination。

案例：Chrome 的多 process 架構

傳統瀏覽器是單一 process，一個網頁出問題整個瀏覽器一起當掉。Chrome 改成多 process：

  • Browser process：管介面、磁碟和網路 I/O。
  • Renderer process：畫網頁、處理 HTML 和 JavaScript，每個網站一個，跑在 sandbox 裡，限制存取磁碟和網路，就算網頁有惡意程式傷害也很小。
  • Plug-in process：每種外掛一個。

代價是很佔記憶體、context switch 變多，而且 process 之間要溝通變麻煩，這就需要 IPC。

IPC：行程間通訊

process 分成兩種：

  • Independent process：不跟別人共用資料，不影響別人也不被影響。
  • Cooperating process：只要和其他 process 共用資料就算。

需要合作的原因：

  • Information sharing：例如從 Chrome 複製一段字貼到 Word。
  • Computation speedup：把大工作拆開平行做，要有多核心才真的變快。
  • Modularity：把系統功能拆成好幾個 process。

cooperating process 用 IPC（inter-process communication）交換資料，有兩種基本方式：

Shared memory
劃一塊記憶體讓大家共用，process 透過讀寫那塊區域交換資料。建立之後 OS 就不介入，所以很快；但資料格式、位置、避免同時寫入（critical section problem）都要 process 自己處理。
Message passing
process 不共用位址空間，透過 OS 提供的 send(message) 和 receive(message) 傳訊息。每次都要經過 kernel，比較慢，但不用自己處理衝突，也特別適合分散式環境。

Shared memory：Producer-Consumer

用 shared memory 溝通時，通常在共享區域放一個 buffer：producer 產生資料放進去，consumer 拿出來用。shared memory 是那塊共用的區域本身（白板），buffer 是 process 自己在上面規劃的資料結構（白板上畫的格子和規則）。unbounded buffer 大小沒有限制，producer 永遠可以放；bounded buffer 大小固定，空了 consumer 要等、滿了 producer 要等。

bounded buffer 常用大小為 BUFFER_SIZE 的 circular array：

  • in：下一個空位，producer 要放的位置
  • out：下一個有資料的位置，consumer 要拿的位置
  • 空：in == out
  • 滿：(in + 1) % BUFFER_SIZE == out

為了分得出空和滿，故意空一格，所以最多只能放 BUFFER_SIZE − 1 筆資料。

Message passing 的三個設計問題

Naming：Direct communication
要明確寫出對方的名字：send(P, message)、receive(Q, message)。link 自動建立，一條 link 只連兩個 process。缺點是對象寫死（hard coded），P 換了就要改所有程式碼。
Naming：Indirect communication
透過 mailbox（也叫 port）交換：send(A, message) 送到 mailbox A。共用同一個 mailbox 才建立 link，一個 mailbox 可以給很多 process 用，送的人不用知道誰會收。如果 P1 送信、P2 和 P3 同時 receive，要靠規則決定：限制一條 link 只連兩個 process、同一時間只允許一個 receive，或由系統選一個並通知送信者。mailbox 可以屬於某個 process（owner 消失 mailbox 就消失）或屬於 OS。
Synchronization
blocking send 送出後等到對方收到才繼續、blocking receive 等到有訊息才繼續；non-blocking send 送出就走、non-blocking receive 有就拿、沒有就拿到 null。send 和 receive 都 blocking 時，雙方要互相等到都到場，叫 rendezvous。
Buffering
還沒被收走的訊息放在附在 link 上、由 OS 管理的 queue。容量有三種：zero capacity（不能放，送的人一定要等收的人）、bounded capacity（放 n 個，滿了要等）、unbounded capacity（送的人永遠不用等）。

Pipes

pipe 是一條讓兩個 process 溝通的管道。設計時要考慮：

  • 單向還是雙向？
  • 雙向的話是 half-duplex（像對講機，一次一個方向）還是 full-duplex（像電話，兩邊同時講）？
  • 一定要有 parent-child 關係嗎？
  • 能不能跨網路？
Ordinary pipe
單向，一定要有 parent-child（血緣）關係。用陣列 fd 表示兩端：fd[0] 是讀取端、fd[1] 是寫入端。parent 用 pipe() 建立後 fork，child 繼承同一組 fd，兩邊就接上同一條管子；沒有血緣關係的 process 拿不到這組 fd。
Named pipe
有名字、像檔案一樣存在檔案系統裡，不需要 parent-child 關係，知道路徑就能打開接上，可以有好幾個 process 一起用，通常只能在同一台機器上。UNIX 的 named pipe（FIFO）是 half-duplex，Windows 支援 full-duplex。
常見錯誤

fork 之後 parent 和 child 都握有讀寫兩端，要各自 close() 用不到的那端。reader 要等到「所有寫入端都關掉」才會讀到 EOF；如果 child 忘了關自己的 fd[1]，parent 寫完關掉後，child 的 read() 還是會一直等，因為它自己就是那個「還可能寫資料的人」。

Socket

socket 讓兩台不同電腦上的程式互相傳訊息。要找到另一台電腦上的某個程式需要兩個資訊：IP 位址（哪一台電腦，例如 140.119.168.10）和 port（那台電腦上的哪個服務，0 至 65535，1 至 1023 由系統保留給標準服務）。三種 socket：

  • Connection-oriented（TCP）：先建立連線再傳，保證送到、順序正確。
  • Connectionless（UDP）：不建立連線直接丟，快但不保證送到。
  • MulticastSocket：一次送給多個接收者（例如 239.x.y.z）。

127.0.0.1 叫 localhost（loopback），指向自己這台電腦；10.x.x.x、172.16 至 172.31.x.x、192.168.x.x 是只在區域網路有效的私有 IP。

RPC：Remote Procedure Call

RPC 讓你像呼叫本地函式一樣呼叫另一台電腦上的函式，常用在分散式系統。關鍵是 stub（存根）：

  • Client 端的 stub：找到 server、把參數 marshal（打包成能在網路上傳的格式）送出。
  • Server 端的 stub：收到後把參數拆開還原，真的執行那個函式，再把結果送回。

兩台電腦存數字的方式可能不同（big-endian 大的那端先放、little-endian 小的那端先放），所以大家約好中立格式 XDR（External Data Representation）：client 先轉成 XDR 送出，server 收到再轉成自己的格式。

RPC 可能失敗，也可能被重複執行：

  • 請求在去程弄丟：server 根本沒收到，沒有執行。
  • 回覆在回程弄丟：server 已經執行了，但 client 以為失敗而重送，結果做了兩次（例如扣款兩次）。

從 client 看這兩種情況一模一樣，所以有兩種保證：

At most once
每個訊息附上 timestamp 當唯一編號，server 記住處理過的編號，重複的就不再執行。保證不會重複，但可能一次都沒做。
Exactly once
在 at most once 之上，server 做完要回 ACK，client 沒收到 ACK 就一直重送，直到收到為止。保證剛好執行一次。

實際例子

fork() 之後誰先印？

#include <stdio.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void) {
    int x = 10;
    pid_t pid = fork();

    if (pid < 0) {
        perror("fork");
        return 1;
    } else if (pid == 0) {
        x = x + 5;
        printf("child : pid=%d, x=%d\n", getpid(), x);
    } else {
        wait(NULL);
        printf("parent: pid=%d, child=%d, x=%d\n", getpid(), pid, x);
    }
    return 0;
}

預期輸出（PID 每次執行都不同）：

child : pid=4012, x=15
parent: pid=4011, child=4012, x=10

一步一步看發生了什麼：

  1. fork() 之前只有一個 process，x = 10。
  2. fork() 之後變成兩個 process，各自有一份 x，值都是 10。
  3. child 拿到的 pid 是 0，進入 else if，把自己的 x 改成 15。
  4. parent 拿到的 pid 是 child 的 PID，進入 else，先 wait(NULL) 等 child 結束，所以一定是 child 先印。
  5. parent 的 x 還是 10，因為兩個 process 的記憶體是分開的，child 改的是自己那份。
記憶技巧

如果把 wait(NULL) 拿掉，誰先印就不一定了，要看 scheduler 怎麼排。考試問「輸出順序」時，先找有沒有 wait()。

連續 fork() 會有幾個 process？

#include <stdio.h>
#include <unistd.h>

int main(void) {
    fork();
    fork();
    printf("hi\n");
    return 0;
}

第一個 fork() 後有 2 個 process，這 2 個都會執行第二個 fork()，各自再分裂一次，變成 4 個。4 個 process 都會執行 printf，所以印出 4 行 hi。一般化：連續 n 個 fork() 會有 2n 個 process。

Ordinary pipe：parent 寫、child 讀

#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void) {
    int fd[2];
    char buf[32];
    pipe(fd);                          /* fd[0] 讀取端，fd[1] 寫入端 */
    if (fork() == 0) {                 /* child：只讀 */
        close(fd[1]);
        ssize_t n = read(fd[0], buf, sizeof(buf) - 1);
        buf[n] = '\0';
        printf("child read: %s\n", buf);
        close(fd[0]);
    } else {                           /* parent：只寫 */
        close(fd[0]);
        const char *msg = "Greetings";
        write(fd[1], msg, strlen(msg));
        close(fd[1]);                  /* 關掉寫入端，child 才會讀到 EOF */
        wait(NULL);
    }
    return 0;
}

預期輸出：child read: Greetings。

shell 的 ls | grep txt 也是 ordinary pipe：shell 先呼叫 pipe()，再 fork 出兩個 child，一個 exec 成 ls 並把輸出接到寫入端，另一個 exec 成 grep 從讀取端讀。真正溝通的是兩個兄弟 process，它們都從同一個 parent 繼承了那組 fd，所以符合「要有血緣關係」的規則。

Circular buffer 最多能放幾筆？

BUFFER_SIZE = 5，一開始 in = out = 0（空）。producer 放了 4 筆後 in = 4，此時 (4 + 1) % 5 = 0 = out，判斷為滿。所以 5 格的 buffer 最多只放 4 筆：如果允許放第 5 筆，in 會繞回 0，和空的時候一樣 in == out，就分不出是空還是滿。

Pseudocode

Context switch

FUNCTION context_switch(old, new)
    // 1. 把目前 CPU 的狀態存進舊 process 的 PCB
    old.pcb.program_counter = CPU.pc
    old.pcb.registers       = CPU.registers
    old.pcb.state           = READY      // 或 WAITING，看切換原因

    // 2. 把舊 process 放回對應的 queue
    IF old.pcb.state == READY THEN
        ready_queue.enqueue(old)
    ELSE
        wait_queue.enqueue(old)
    END IF

    // 3. 從新 process 的 PCB 載入狀態
    CPU.registers  = new.pcb.registers
    CPU.pc         = new.pcb.program_counter
    switch_address_space(new.pcb.page_table)
    new.pcb.state  = RUNNING
END FUNCTION

Shell 怎麼執行一個指令

WHILE true
    command = read_line()
    pid = fork()
    IF pid == 0 THEN
        // child：換成使用者要跑的程式
        exec(command)
        print("command not found")   // exec 成功的話不會跑到這行
        exit(1)
    ELSE
        // parent：等 child 跑完再顯示下一個提示字元
        wait(pid)
    END IF
END WHILE

Producer-Consumer（shared memory，busy waiting 版本）

// 共享的變數
buffer[BUFFER_SIZE]
in = 0
out = 0

// Producer
WHILE true
    item = produce()
    WHILE (in + 1) % BUFFER_SIZE == out
        // buffer 滿了，什麼都不做，一直等
    END WHILE
    buffer[in] = item
    in = (in + 1) % BUFFER_SIZE
END WHILE

// Consumer
WHILE true
    WHILE in == out
        // buffer 空了，一直等
    END WHILE
    item = buffer[out]
    out = (out + 1) % BUFFER_SIZE
    consume(item)
END WHILE
補充

這個版本只是示範，會浪費 CPU 空轉，而且如果改成用一個 counter 記錄 buffer 裡有幾筆，就會出現 race condition，這是第 06 章同步的出發點。

三種 scheduler

Scheduler負責的轉換頻率重點
Long-termnew → ready很低（秒到分鐘）控制 degree of multiprogramming、混合 I/O-bound 與 CPU-bound
Short-termready → running很高（毫秒）一定要快
Medium-termswap out / swap in記憶體不夠時暫時降低記憶體裡的 process 數量

IPC 方法

方法需要血緣關係跨機器特點
Shared memory否否建立後不經過 kernel，最快；同步要自己處理
Message passing否可以每次經過 kernel，較慢；不用處理衝突
Ordinary pipe是否單向，fd[0] 讀、fd[1] 寫
Named pipe否通常否有名字、存在檔案系統，UNIX half-duplex、Windows full-duplex
Socket否是IP + port，TCP 可靠、UDP 快
RPC否是像呼叫本地函式，靠 stub 和 XDR

自我測驗

Q1. 下面的程式會印出幾行 hi？fork(); fork(); fork(); printf("hi\n");

答案：8 行。

原因：每執行一次 fork()，目前存在的每個 process 都會分裂成兩個。1 → 2 → 4 → 8，最後 8 個 process 都會執行 printf。

Q2. 一個 process 在 running 狀態時呼叫 scanf() 等使用者輸入，它會變成什麼狀態？使用者按下 Enter 後呢？

答案：先變成 waiting，使用者輸入完成後變成 ready。

原因：等輸入的時候給它 CPU 也沒用，所以作業系統把它移到 waiting，讓別人用 CPU。輸入完成只代表它可以繼續跑了，但還是要回 ready queue 排隊，等 scheduler 選到它才會再變成 running。

Q3. 為什麼 time slice 設得非常小（例如每 1 微秒就切換一次）反而會讓系統變慢？

答案：因為 context switch 本身要花時間，而且這段時間 CPU 沒有做有用的工作。

原因：如果每次切換的成本和 time slice 差不多長，CPU 幾乎一半的時間都花在存、讀 PCB 上。另外切換後 cache 裡的資料大多是上一個 process 的，新的 process 一開始會一直 cache miss，速度也會變慢。

Q4. 在「實際例子」的第一段程式裡，parent 印出的 x 為什麼是 10 而不是 15？

答案：因為 parent 和 child 的記憶體是分開的。

原因：fork() 會幫 child 建立一份 parent 位址空間的複本（實作上通常用 copy-on-write，真的寫入時才複製），child 修改的是自己那份 x，不會影響 parent。如果想讓兩者看到同一份資料，要用 shared memory 之類的 IPC 機制。

Q5. 用 ordinary pipe 時，child 只負責讀，卻忘了 close(fd[1])。parent 寫完資料並關掉自己的 fd[1] 之後，child 會發生什麼事？

答案：child 讀完資料後，read() 會一直卡住，永遠等不到 EOF。

原因：OS 要等到所有寫入端都關掉，才會告訴 reader 已經讀完。fork 之後寫入端其實有兩個：parent 的和 child 自己的。child 沒關自己那個，OS 就認為還可能有人寫入，blocking 的 read() 只能一直等。

Q6. RPC 呼叫「扣款 100 元」送出後一直沒收到回覆，client 直接重送。在什麼情況下會扣款兩次？要怎麼避免？

答案：server 其實收到也扣款了，只是回覆在回程弄丟，重送就會再扣一次。可以用 at most once 或 exactly once 語意避免。

原因：client 分不出「server 沒收到」和「server 做了但回覆不見」。at most once 讓每個請求帶唯一的 timestamp，server 看到處理過的編號就不再執行；exactly once 再加上 ACK，client 沒收到 ACK 就重送，server 靠編號擋掉重複，確保剛好執行一次。

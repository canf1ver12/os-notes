CHAPTER 07

同步範例

Synchronization Examples

本章重點

  • 這章用上一章的 semaphore 和 monitor，解三個經典的同步問題：bounded buffer、readers-writers、dining philosophers。
  • Bounded buffer 要三個 semaphore：mutex 保護 buffer、empty 數空位、full 數產品，因為對生產者和消費者來說「資源」的意義不同。
  • Readers-writers 允許很多 reader 同時讀，但 writer 要獨佔；先照顧 reader 的版本 writer 可能 starvation，先照顧 writer 的版本 reader 可能 starvation。
  • Dining philosophers 如果每個人都先拿左邊的筷子，可能 deadlock；用 monitor 規定「兩支筷子都有才能拿」就能避免。
  • 實際寫程式時，POSIX 用 sem_init、sem_wait、sem_post；Java 有 Semaphore 類別，也能用 synchronized 把物件變成 monitor。

核心觀念

Bounded-buffer problem

這就是第 03 章看過的 producer-consumer 問題，現在用 semaphore 來解。共用一個有 n 格的 buffer，每格放一個 item：

  • Producer：拿一個空格、把 item 放進去；沒有空格時要等。
  • Consumer：從 buffer 拿走一個 item、把空格還回去；buffer 全空時要等。

需要三個 semaphore：

mutex = 1
當 boolean 用，控制 critical section，同一時間只有一個人能改 buffer。
empty = n
管控空位的個數，producer 放東西前要先 wait(empty)。
full = 0
管控產品的個數，consumer 拿東西前要先 wait(full)。

為什麼同時要有 empty 和 full？因為對生產者和消費者來說，「資源」的意義不同。生產者要的資源是空位，消費者要的資源是產品，兩個人等的東西不一樣，所以各用一個計數器。

  • producer 放完之後 signal(full)：產品加一，叫醒可能在等的消費者。
  • consumer 拿完之後 signal(empty)：空位加一，叫醒可能在等的生產者。
常見錯誤

wait 的順序要先等資源，再拿鎖。如果 producer 寫成先 wait(mutex) 再 wait(empty)，buffer 滿的時候它會拿著 mutex 去睡覺等空位，但 consumer 要先拿到 mutex 才能拿走東西、產生空位，兩邊互相等，就 deadlock 了。

Readers-writers problem

好幾個 process 共用一個資料庫，分成兩種：

Reader
只讀資料。很多個 reader 可以同時讀，因為讀不會改到資料。
Writer
會讀也會寫。同一時間只能有一個 writer，而且寫的時候也不能有人在讀。

依照優先順序的不同，有兩種版本：

  • First readers-writers problem：一旦 reader 拿到鎖，要等所有 reader 都讀完才會釋放，所以只要一直有 reader 進來，writer 可能 starvation。
  • Second readers-writers problem：writer 一旦準備好，就不能再有新的 reader 開始讀，所以換成 reader 可能 starvation。

First readers-writers 的做法

需要兩個 semaphore 和一個計數器：

rw_mutex = 1
保護資料庫，reader 和 writer 共用，防止 writer 在別人讀的時候寫入。
mutex = 1
保護 read_count，只有 reader 之間共用。
read_count = 0
現在有幾個 reader 在讀。
  • Writer：直接 wait(rw_mutex)，寫完 signal(rw_mutex)。
  • 第一個 reader（read_count 從 0 變 1）：代表所有 reader 去拿 rw_mutex，拿到之後後面的 reader 都能直接進來讀。
  • 最後一個 reader（read_count 從 1 變 0）：代表所有 reader 釋放 rw_mutex，writer 才能進去。

生活例子：圖書館的閱覽室，第一個進去的讀者開燈並掛上「閱讀中」的牌子，後面的讀者看到燈亮著就直接進去；最後一個離開的讀者才關燈拿掉牌子，要整理書架的館員（writer）這時才能進去。只要讀者一直來，館員就一直進不去。

Dining-philosophers problem

5 個哲學家坐在圓桌的 5 張椅子上，桌上只有 5 支筷子，每兩個人中間放一支。

  • 哲學家不是在思考就是在吃飯。思考時不會和其他 4 個人互動。
  • 吃飯需要手上有 2 支筷子，而且一次只能拿起 1 支。
  • 吃完就把兩支筷子都放下。

這個問題包含了同步的三種難題：

  • 資源競爭：一支筷子同時只能被一個人拿著（mutual exclusion）。
  • Deadlock：大家都卡住，沒人能吃（progress）。
  • Starvation：某個人一直吃不到（bounded waiting）。

錯誤解法：每個人先拿左邊

每支筷子用一個初始值 1 的 semaphore 表示。哲學家 i 先 wait 左邊的筷子 chopstick[i]，再 wait 右邊的筷子 chopstick[(i+1) % 5]，吃完再兩支都 signal。

問題是：如果 5 個人同時肚子餓，每個人都剛好拿起自己左邊的筷子，5 支筷子全被拿走，每個人都在等右邊的人放下筷子，但沒有人會放，就 deadlock 了。

可能的解法：

  1. 最多只讓 4 個人同時坐在桌邊：4 個人分 5 支筷子，至少有一個人能拿到兩支。
  2. 兩支筷子都有空才能拿：要拿就一次拿兩支，不會拿著一支卡住。下面的 monitor 解法就是這個做法。
  3. 不對稱：奇數號的人先拿左邊再拿右邊，偶數號的人先拿右邊再拿左邊，打破所有人都在等同一個方向的循環。

Dining philosophers 的 monitor 解法

monitor DiningPhilosophers 裡面有：

  • state[5]：每個哲學家的狀態，thinking、hungry 或 eating。
  • condition self[5]：每個哲學家一個 condition variable，拿不到筷子時就在自己的 self[i] 上等。
  • pickup(i)、putdown(i)、test(i) 三個 method。

為什麼要用 condition variable？因為要指定「特定的哪個哲學家」去等或被叫醒，monitor 本身的 entry queue 做不到這件事。

  • test(i)：檢查哲學家 i 能不能開始吃。條件是自己餓了，而且左右兩邊的人都沒在吃。成立就把 state[i] 改成 eating，並 self[i].signal()。
  • pickup(i)：把自己設成 hungry，呼叫 test(i) 試著吃；如果沒有變成 eating（剛好隔壁有人在吃），就 self[i].wait() 等待被叫醒。
  • putdown(i)：吃飽後設成 thinking，然後幫左右兩邊各 test 一次，給他們各一次吃飯的機會。

使用方式是每個哲學家 i 都依序呼叫 DiningPhilosophers.pickup(i)、吃飯、DiningPhilosophers.putdown(i)。這個解法不會 deadlock，但有可能某個哲學家一直被左右輪流搶先，還是可能 starvation。

POSIX semaphore

POSIX 提供的 semaphore 函式：

sem_init(sem_t *sem, int pshared, unsigned int value)
建立 semaphore。pshared 設定能不能讓不同 process 共用，設成 0 就只能給同一個 process 的 thread 用；value 是初始值，也就是一開始有多少資源。
sem_wait(sem_t *sem)
等同於 wait。
sem_post(sem_t *sem)
等同於 signal。
sem_getvalue(sem_t *sem, int *valptr)
讀出 semaphore 目前的值。
sem_destroy(sem_t *sem)
用完後銷毀 semaphore。

Java semaphore 和 Java monitor

Java 的 java.util.concurrent.Semaphore 用建構子 Semaphore(int value) 設定初始值，acquire() 等同 wait、release() 等同 signal。

Java 也內建 monitor 的概念：

  • 每個 Java 物件都有一個鎖。
  • 把 method 宣告成 synchronized，就會變成 monitor：呼叫的 thread 要先拿到這個物件的鎖才能執行。
  • 拿不到鎖的其他 thread 在 entry set 裡等待。
補充

注意是 entry set 不是 list，set 不保證次序，所以先來等的 thread 不一定先拿到鎖。

實際例子

追蹤 bounded buffer 的三個 semaphore

buffer 有 3 格，一開始 empty = 3、full = 0、mutex = 1。producer 和 consumer 依下面的順序執行（mutex 每次都拿了又放回 1，表格省略）：

步驟動作emptyfullbuffer說明
0初始30空3 個空位、0 個產品
1P 放入 A21Await(empty) 減一，signal(full) 加一
2P 放入 B12A B
3C 拿走 A21Bwait(full) 減一，signal(empty) 加一
4P 放入 C12B C
5P 放入 D03B C Dbuffer 滿了
6P 想放入 E−13B C D沒空位，P 在 empty 上 sleep
7C 拿走 B02C Dsignal(empty) 後仍小於等於 0，叫醒 P
8P 醒來放入 E03C D Esignal(full) 加一

第 6 步 producer 被卡住，要等第 7 步 consumer 的 signal(empty) 才能再寫入，這就是 empty 的用途。

為什麼 first readers-writers 會讓 writer 餓死

時間事件read_countrw_mutex 在誰手上
1R1 進來讀，是第一個 reader，拿 rw_mutex1reader 們
2R2 進來讀，不用再拿 rw_mutex2reader 們
3W 想寫，wait(rw_mutex)，只能等2reader 們

W 在第 3 步就到了，卻要等到第 6 步。如果 R3 之後一直有新的 reader 在 read_count 還沒歸零前進來，W 就會永遠等下去。

Dining philosophers 的 monitor 解法實際跑一次

一開始 5 個哲學家都在 thinking。P1 和 P2 是鄰居，先後想吃飯：

步驟呼叫發生什麼事P1P2
1P1：pickup(1)state[1] = hungry，test(1)：左邊 P0、右邊 P2 都沒在吃，成立eatingthinking
2P2：pickup(2)state[2] = hungry，test(2)：左邊 P1 正在吃，不成立，所以 self[2].wait()eatinghungry（等待中）
3P1：putdown(1)state[1] = thinking，test(0)：P0 沒有餓，什麼都不做thinkinghungry（等待中）
4（putdown 繼續）test(2)：P2 餓了，左邊 P1、右邊 P3 都沒在吃，成立，state[2] = eating，self[2].signal()thinkingeating
5P2：putdown(2)吃完放下筷子，回到 thinkingthinkingthinking

第 2 步 P2 不會拿著一支筷子等，而是什麼都沒拿就在 self[2] 上等，這就是「兩支都有才拿」的意思，所以不會出現每個人都拿著一支的 deadlock。

用 POSIX semaphore 寫 bounded buffer

#include <stdio.h>
#include <pthread.h>
#include <semaphore.h>

#define BUFFER_SIZE 5
#define ITEMS 10

int buffer[BUFFER_SIZE];
int in = 0, out = 0;

sem_t mutex;    // 控制 critical section，初始 1
sem_t empty;    // 空位數，初始 BUFFER_SIZE
sem_t full;     // 產品數，初始 0

void *producer(void *arg) {
    for (int item = 1; item <= ITEMS; item++) {
        sem_wait(&empty);              // 等到有空位
        sem_wait(&mutex);
        buffer[in] = item;
        in = (in + 1) % BUFFER_SIZE;
        sem_post(&mutex);
        sem_post(&full);               // 產品 +1，叫醒可能在等的消費者
    }
    return NULL;
}

void *consumer(void *arg) {
    int sum = 0;
    for (int i = 0; i < ITEMS; i++) {
        sem_wait(&full);               // 等到有產品
        sem_wait(&mutex);
        int item = buffer[out];
        out = (out + 1) % BUFFER_SIZE;
        sem_post(&mutex);
        sem_post(&empty);              // 空位 +1，叫醒可能在等的生產者
        printf("consumed %d\n", item);
        sum += item;
    }
    printf("sum = %d\n", sum);
    return NULL;
}

int main(void) {
    sem_init(&mutex, 0, 1);            // pshared = 0：只給同一個 process 的 thread 用
    sem_init(&empty, 0, BUFFER_SIZE);
    sem_init(&full, 0, 0);

    pthread_t p, c;
    pthread_create(&p, NULL, producer, NULL);
    pthread_create(&c, NULL, consumer, NULL);
    pthread_join(p, NULL);
    pthread_join(c, NULL);

    sem_destroy(&mutex);
    sem_destroy(&empty);
    sem_destroy(&full);
    return 0;
}

編譯：gcc bounded_buffer.c -o bounded_buffer -pthread

預期輸出：依序印出 consumed 1 到 consumed 10，最後印 sum = 55。buffer 是 FIFO，所以不管兩個 thread 怎麼交錯，消費的順序都和生產的順序一樣。

補充

macOS 不支援 sem_init 這種沒有名字的 semaphore（編譯會有 deprecated 警告，執行時會失敗），這段程式請在 Linux 上跑。macOS 上要改用 sem_open 建立有名字的 semaphore，細節依系統而異。

First readers-writers

semaphore rw_mutex = 1   // 保護資料庫，reader 和 writer 共用
semaphore mutex = 1      // 保護 read_count，reader 之間共用
read_count = 0

// Writer
WHILE true
    wait(rw_mutex)
    // 寫入資料
    signal(rw_mutex)
END WHILE

// Reader
WHILE true
    wait(mutex)
    read_count = read_count + 1
    IF read_count == 1 THEN      // 第一個 reader
        wait(rw_mutex)           // 代表所有 reader 拿鎖
    END IF
    signal(mutex)

    // 讀取資料

    wait(mutex)
    read_count = read_count - 1
    IF read_count == 0 THEN      // 最後一個 reader

    END IF
    signal(mutex)
END WHILE

Dining philosophers：monitor 解法

MONITOR DiningPhilosophers
    state[5]                 // THINKING、HUNGRY、EATING
    condition self[5]        // 拿不到筷子時在這裡等

    FUNCTION pickup(i)       // 哲學家 i 想拿筷子
        state[i] = HUNGRY
        test(i)
        IF state[i] != EATING THEN
            self[i].wait()   // test 失敗，隔壁有人在吃，等待被叫醒
        END IF
    END FUNCTION

    FUNCTION putdown(i)      // 吃飽後放下筷子
        state[i] = THINKING
        test((i + 4) % 5)    // 給左邊一次機會
        test((i + 1) % 5)    // 給右邊一次機會
    END FUNCTION

    FUNCTION test(i)         // 左右都沒在吃，而且自己餓了，才能開始吃
        IF state[(i + 4) % 5] != EATING
           AND state[i] == HUNGRY
           AND state[(i + 1) % 5] != EATING THEN
            state[i] = EATING
            self[i].signal() // 開始吃
        END IF
    END FUNCTION

    FUNCTION initialization_code()
        FOR i = 0 TO 4
            state[i] = THINKING
        END FOR
    END FUNCTION
END MONITOR

DiningPhilosophers.pickup(i)

自我測驗

Q1. Bounded buffer 已經有 mutex 了，為什麼還需要 empty 和 full 兩個 semaphore？只用一個 count 可以嗎？

答案：需要兩個，因為生產者和消費者要等的資源不同，生產者等空位、消費者等產品。

原因：mutex 只保證同時只有一個人改 buffer，不會告訴你 buffer 有沒有空位或有沒有東西。生產者在 buffer 滿時要睡在「空位」上，消費者在 buffer 空時要睡在「產品」上，兩邊被叫醒的條件不一樣，所以各用一個 semaphore，讓 signal(full) 只叫醒消費者、signal(empty) 只叫醒生產者。

Q2. 如果 consumer 寫成先 wait(mutex) 再 wait(full)，什麼情況下會出事？

答案：buffer 是空的時候會 deadlock。

原因：consumer 拿著 mutex 去等 full，但 producer 要放東西進 buffer 之前也要先拿 mutex，拿不到就放不進去，full 永遠不會增加。兩邊互相等對方手上的東西，就是 deadlock。所以要先等資源，再拿鎖。

Q3. First readers-writers 裡，為什麼只有「第一個」reader 要 wait(rw_mutex)、「最後一個」reader 要 signal(rw_mutex)？

答案：因為很多 reader 可以同時讀，只要有一個 reader 拿到鎖，就代表整群 reader 擋住 writer。

原因：如果每個 reader 都 wait(rw_mutex)，rw_mutex 初始值是 1，第二個 reader 就會被擋住，reader 就不能同時讀了。所以用 read_count 數人數，第一個進來的負責拿鎖、最後一個離開的負責放鎖，中間的 reader 直接進出。

Q4. 5 個哲學家都先拿左邊的筷子，為什麼可能 deadlock？「最多只讓 4 個人坐下」為什麼能解決？

答案：5 個人同時拿起左邊的筷子後，每個人都在等右邊的人放下，形成循環等待。只讓 4 個人坐下時，至少有一個人能拿到兩支筷子。

原因：4 個人分 5 支筷子，就算每個人都先拿起一支，還剩 1 支，坐在它旁邊的那個人一定能拿到第二支。他吃完放下兩支筷子後，旁邊的人也能接著吃，所以不會全部卡住。

Q5. Monitor 解法的 pickup 裡，test(i) 失敗後為什麼要 self[i].wait()？之後是誰把他叫醒？

答案：test 失敗代表左邊或右邊有人正在吃，只能等。之後由旁邊吃完的人在 putdown 裡呼叫 test(i)，成立時用 self[i].signal() 把他叫醒。

原因：每個哲學家有自己的 condition variable self[i]，所以能精準地叫醒「特定的那個人」。鄰居 putdown 時會幫左右各 test 一次，如果這個人還餓、而且兩邊都沒在吃，就把他設成 eating 並叫醒。

Q6. 好幾個 thread 在等同一個 Java 物件的 synchronized method，最早來等的 thread 一定會最先拿到鎖嗎？

答案：不一定。

原因：拿不到鎖的 thread 是放在 entry set 裡等，set 不保證次序，所以 JVM 選誰拿鎖不一定照到達的順序。

作業系統結構

OS Structure

本章重點

  • 使用者透過 CLI、GUI、觸控或語音介面使用 OS；程式則透過 system call 請 OS 幫忙。
  • 我們平常呼叫的是 API（system call 的包裝），API 帶來 portability 和 ease of use；printf 是厚包裝，open 是薄包裝。
  • 傳參數給 OS 有三種方法：register、記憶體中的 block / table、stack；system call 分成六大類。
  • Linker 把程式和函式庫接起來（static 或 dynamic linking），loader 把執行檔載進記憶體並處理 relocation；Linux 的執行檔格式是 ELF。
  • OS 設計重視 policy 與 mechanism 分離；結構從 monolithic、layered、microkernel、modules 到現代常見的 hybrid。

核心觀念

User interface

  • CLI（Command Line Interface）：處理指令的程式叫 shell（bash、ksh、csh、tcsh），工作是 parse、search、execute。指令分兩種：內建指令 shell 本來就認識；外部指令 shell 照 PATH 設定去找第一個符合的程式。
  • GUI：用圖示代表檔案和程式，用滑鼠操作。現在大部分系統同時有 CLI 和 GUI。
  • TUI（Touch）：用手勢操作，是手機的標準介面；VUI（Voice）：用聲音互動。

System call

System call 是程式和 OS 之間的介面：透過 software interrupt（trap）明確地請 kernel 做事。最底層是組合語言指令，而且一個簡單的動作常常需要好幾個 system call 才能完成。

比喻：你不能自己走進銀行金庫拿錢，只能到櫃台填單，由行員（kernel）幫你處理。填單這個動作就是 system call。

API：System call 的包裝

直接用 system call 要自己把參數塞進特定暫存器、再觸發 trap，很麻煩。API（Application Program Interface）把這些包成普通的函式（例如 POSIX API、Windows API）。好處：

  1. Portability：每個 OS 的 system call 名稱、編號、傳參數方式都不同，只要遵守 POSIX 這種標準 API，程式換到別的系統重新編譯就能跑。
  2. Ease of use：API 幫你處理參數和錯誤碼等細節，呼叫者完全不用知道 kernel 裡怎麼實作。
薄包裝：open()
API 叫 open()，底下的 system call 也叫 open，幾乎一對一直通。API 只是把參數放對位置、填上編號、觸發 trap。
厚包裝：printf()
kernel 裡根本沒有 printf，只認得 write。printf 是 C 函式庫（Linux 下是 glibc）先處理格式（把 42 轉成字元 '4' '2'），再呼叫 write 這個 system call。C 的 printf、C++ 的 cout、Python 的 print，最後把字送到螢幕的都是同一個 write。
記憶技巧

Linux 上可以用 strace 指令看一個程式執行時呼叫了哪些 system call，man read 可以查 read() 這個 API 的規格。

傳參數給 OS 的三種方法

  1. 放在 register：最簡單、最快，但參數可能比 register 還多。
  2. 放在記憶體的 block / table：把參數存在一塊記憶體，再把那塊的位址放進 register，kernel 拿位址去讀。
  3. push 到 stack：kernel 再從 stack pop 出來用。

後兩種不限制參數的數量和長度。原則是：東西太大或太多，就不傳東西本身，改傳它在哪裡。

System call 的六大類

Process control
create / terminate process、load / execute、end()（正常結束）與 abort()（不正常中止，會 dump 記憶體內容方便 debugger 找 bug）、wait、allocate / free memory。
File manipulation
create / delete、open / close、read / write / reposition（移動讀寫位置）、get / set file attributes。
Device manipulation
request / release device（例如 Zoom 先 request 了攝影機，其他程式只能等它 release）、read / write、logically attach / detach devices。
Information maintenance
get / set time or date、system data、process / file / device 的屬性。
Communication
create / delete connection、send / receive messages、attach / detach remote devices。
Protection
get / set file permissions，Unix 的 chmod 就是在做這個。
  • Unix 把所有東西都包成檔案，所以裝置也能共用 read() / write()。
  • 檔案做不到的事（例如輸入密碼時不顯示、調整終端機大小）交給 ioctl()。
  • 每個程式一啟動，OS 就開好三個 file descriptor：0 = stdin、1 = stdout、2 = stderr。
  • 之後 open() 一個檔案，OS 回傳一個小整數（例如 3），代表它記在這個 process 的已開啟檔案表第 3 格，之後讀寫只要拿這個號碼。

Single-task 與 Multi-task 的 process control

Arduino 沒有 OS，只有一個 boot loader：一次只能跑一個程式（sketch），sketch 獨佔整個記憶體，要換程式只能把新的燒進去覆蓋舊的。FreeBSD 這種 Unix 系統可以同時跑很多程式：shell 用 fork() 建立 process、exec() 載入程式，程式結束時回傳 exit code（0 代表沒有錯誤，大於 0 是錯誤碼）。

System services

也叫 system utilities，是 OS 附帶的一堆小工具程式，提供方便的開發和執行環境。一般使用者不會自己寫程式呼叫 open()、read()，而是直接用 cp 這種工具，由工具去呼叫 system call，所以它們是使用者和 system call 之間的中間人。

Linker 與 Loader

  • Compiler：把 C 程式翻成機器碼（relocatable object file）。遇到 sqrt 只留一個空格：「這裡要呼叫 sqrt，但不知道它在哪」。
  • Linker：把 .o 和函式庫拼在一起、填上空格，產出可執行檔。
  • Loader：執行時把執行檔搬進記憶體，並負責 relocation：因為 swapping、virtual memory，程式被放的位置可能改變，程式裡的位址必須用相對的。如果寫死 call 1050，程式被搬到 5000 號開始的地方後就會跳錯位置。
Static linking
編譯時直接把函式庫的程式碼複製進執行檔，產出一個獨立的 single binary，搬到同 OS、同架構的電腦就能跑。
Dynamic linking
執行檔只記錄「需要某個函式庫」，程式啟動時 loader 才去找來接上（例如 Windows 的 DLL）。找不到函式庫就跑不起來。
ELF（Executable and Linkable Format）
UNIX / Linux 的 object file 與執行檔格式，裡面有機器碼和 symbol table（記錄函式、變數名稱，linker 靠它知道空格要填什麼）。

OS 設計原則

設計目標分成兩種，而且常互相衝突，要依目標做 trade-off：

  • User goals：好用、好學、可靠、安全、快
  • System goals：好設計、好實作、好維護、有效率

常用的軟體工程技巧：abstraction、encapsulation 與 information hiding、modularization（例如 LKM）、separation of concerns、low coupling 與 high cohesion、interface 與 implementation 分離。

最常考的是 separation of policy and mechanism：

  • Policy：要做什麼，依情況而定，透過參數或設定檔調整。
  • Mechanism：怎麼做，相對穩定。
  • 兩者分開，改策略時就不用改底層程式。例如 timer 是保護 CPU 的 mechanism，「某個使用者的 timer 要設多長」是 policy。

實作語言：早期用組合語言，現在混合使用，最底層用組合語言，主體用 C / C++，系統程式還會用 shell script、Python 等。效能分析可以用 perf 這類工具看花了多少時間、執行多少指令。

OS 的結構

Monolithic（單體式）
所有 OS 功能都放在 kernel 這一個大程式裡，彼此直接呼叫。效能好，但難以維護和擴充。早期 Unix、MS-DOS（simple structure，沒有清楚分層，應用程式甚至能直接碰硬體）屬於這類。
Layered（分層式）
把 OS 拆成好幾層，最底層是硬體、最上層是使用者介面，第 i 層只使用第 i−1 層提供的服務、只提供服務給第 i+1 層。loosely coupled、好除錯（由下往上一層一層驗證），但每次呼叫要穿過很多層，效能較差，而且很難決定每個功能該放哪一層。
Microkernel（微核心）
kernel 只保留最基本的功能（行程間通訊、基本記憶體管理、CPU scheduling），其他服務（檔案系統、driver）移到 user space，元件之間用 message passing 溝通。容易擴充、移植，可靠又安全（一個服務掛掉不會拖垮 kernel）；缺點是訊息傳遞和模式切換的 overhead 讓效能變差。
Modules（LKM）
Loadable Kernel Modules：kernel 有核心元件，其他功能做成模組，需要時才動態載入（例如插上新裝置才載入 driver）。每個模組有定義好的介面，像 layered 但更有彈性，又因為模組在 kernel 裡直接呼叫，不需要 message passing，效能比 microkernel 好。Linux 就是這樣。
Hybrid（混合式）
現實中大部分現代 OS 混合多種做法，在效能、安全、彈性之間取平衡。

案例：macOS / iOS 與 Android

macOS 和 iOS 上層不一樣（一個用滑鼠、一個用觸控），底下共用 Darwin 核心。Darwin 是 hybrid：包含 Mach microkernel（記憶體管理、IPC、排程）和 BSD UNIX 的部分（POSIX API、網路、檔案系統），也支援動態載入的 kernel extensions。

Android（Google 主導、開源）由下往上是：

  1. Linux kernel：管理 process、記憶體、driver
  2. HAL（hardware abstraction layer）：讓上層用同一套方式操作各家硬體
  3. Native libraries 與 ART（Android Runtime）：執行 .java → .class → .dex 編譯出來的程式
  4. Android framework：開相機、發通知等現成 API
  5. Applications

實際例子

printf("Hello") 背後的四個步驟

#include <stdio.h>

int main(void) {
    printf("Hello\n");
    return 0;
}
  1. 程式在 user mode 呼叫 printf()（API）。
  2. C 函式庫 glibc 攔截這個呼叫，把格式字串處理好。
  3. glibc 呼叫真正的 system call write(1, "Hello\n", 6)，1 就是 stdout 的 file descriptor；這一步觸發 trap 進入 kernel mode。
  4. kernel 把字送到螢幕，write() 回傳寫了幾個 byte，glibc 再把結果傳回程式。

在 Linux 上用 strace ./hello 執行，輸出最後會看到類似 write(1, "Hello\n", 6) = 6 的一行（前面還有很多載入程式、函式庫用的 system call，依系統而異）。

Static 還是 Dynamic linking？

假設電腦上有 100 個程式都用到同一個數學函式庫：

情境Static linkingDynamic linking
硬碟空間100 個執行檔各有一份函式庫硬碟上只要一份
記憶體同時執行時各自載入一份記憶體裡可以只載入一份大家共用
函式庫發現安全漏洞100 個程式全部要重新編譯只要更新那一份，程式下次啟動就用新版
搬到另一台電腦沒裝函式庫也能跑那台沒有函式庫就跑不起來

Pseudocode

API 怎麼把呼叫變成 system call

// user mode：函式庫裡的 open()
FUNCTION open(path, flags)
    register[0] = SYSCALL_OPEN       // system call 編號
    register[1] = address_of(path)   // 參數太大，傳位址
    register[2] = flags
    trap()                           // 進入 kernel mode
    RETURN register[0]               // 回傳 file descriptor 或錯誤碼
END FUNCTION

// kernel mode：trap handler
FUNCTION syscall_handler()
    n = register[0]
    result = system_call_table[n](register[1], register[2])
    register[0] = result
    return_from_trap()               // 回到 user mode
END FUNCTION

Shell：parse、search、execute

WHILE true
    line = read_line()
    command, args = parse(line)
    IF command IS builtin THEN
        run_builtin(command, args)
    ELSE
        path = search_in_PATH(command)       // 找第一個符合的執行檔
        pid = fork()
        IF pid == 0 THEN
            exec(path, args)
        ELSE
            wait(pid)
        END IF
    END IF
END WHILE

cp 背後的 system call 順序

FUNCTION copy(src, dst)
    in  = open(src, READ)             // 失敗就印錯誤並 abort
    out = open(dst, WRITE | CREATE)
    WHILE (n = read(in, buffer)) > 0
        write(out, buffer, n)
    END WHILE
    close(in)
    close(out)
    exit(0)                           // 正常結束
END FUNCTION

自我測驗

Q1. printf 是不是 system call？它最後用到哪一個 system call？

答案：不是。printf 是 C 函式庫的 API，最後呼叫的是 write。

原因：kernel 只認得 write，printf 這個名字在 kernel 裡根本不存在。printf 先在 user mode 把格式處理好（例如把數字轉成字元），再把整理好的字串交給 write 這個 system call 寫到 file descriptor 1（stdout）。

Q2. 一個 system call 需要傳 8 個參數，但 CPU 只有 6 個可用的 register，該怎麼辦？

答案：把參數存在記憶體的一個 block / table 裡，只把這塊記憶體的位址放進 register；或是把參數 push 到 stack。

原因：register 數量固定，參數一多就放不下。改用 block / table 或 stack 就不受參數數量和長度的限制，kernel 拿到位址後自己去記憶體把參數讀出來。

Q3. 「CPU scheduler 每次給一個 process 10 ms」這句話裡，哪個部分是 policy、哪個部分是 mechanism？

答案：用 timer 中斷把 CPU 拿回來、切換 process 是 mechanism；「10 ms」這個時間長度是 policy。

原因：mechanism 回答「怎麼做」，不管給多長的時間都是用同一套 timer 和 context switch；policy 回答「要做什麼」，10 ms 可能依系統用途改成 5 ms 或 20 ms，透過參數調整就好，不需要改底層程式。

Q4. Microkernel 比 monolithic kernel 安全，為什麼大部分 OS 還是沒有採用純 microkernel？

答案：因為效能。microkernel 的服務都在 user space，彼此要靠 message passing，每次溝通都要經過 kernel、切換模式和複製訊息。

原因：monolithic 的元件在同一個 kernel 裡直接呼叫函式，幾乎沒有額外成本。所以現代 OS 多半走 hybrid 或 modules：保留模組化的好處，但讓關鍵服務留在 kernel 裡直接呼叫，例如 Linux 的 LKM、macOS 的 Darwin。

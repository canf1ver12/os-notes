CHAPTER 08

死結

Deadlocks

本章重點

  • Deadlock（死結）是一群 thread 都在等「只有這群裡的另一個 thread 才能觸發」的事件，四個必要條件 mutual exclusion、hold and wait、no preemption、circular wait 同時成立才會發生。
  • 用 resource-allocation graph（資源配置圖）來看：沒有 cycle 就一定沒有 deadlock；有 cycle 時，每種資源只有一個 instance 就一定 deadlock，有好幾個 instance 只是「可能」deadlock。
  • 處理方式分四類：直接忽略（Linux、Windows 都這樣做）、prevention 事先防範（破壞其中一個條件）、avoidance 邊走邊看邊閃（只在配置後仍是 safe state 時才答應）、detection 加 recovery（讓它發生，再偵測和復原）。
  • Banker's algorithm（銀行家演算法）用 Need = Max − Allocation 找 safe sequence，用來處理每種資源有好幾個 instance 的 avoidance。
  • Detection 在單一 instance 時找 wait-for graph 的 cycle，好幾個 instance 時用和 safety algorithm 很像的偵測演算法，只是把 Need 換成目前的 Request；發現後用終止 process 或搶資源來復原。

核心觀念

Deadlock 的定義

一組 thread 處於 deadlock（死結）狀態，是指這組裡的每一個 thread 都在等一個事件，而這個事件只有這組裡的另一個 thread 才能觸發。這裡的「事件」主要是資源的取得和釋放。

生活例子：一條只容得下一台車的窄橋，兩台車從兩頭同時開上來，在中間對上了。兩台車都要對方先倒車才能過，但兩台都在等對方，誰也不動，就卡死了。

第 06 章的 liveness 已經看過最小的例子：P0 先 wait(S) 再 wait(Q)，P1 先 wait(Q) 再 wait(S)，兩邊各拿一個再等對方，就 deadlock 了。這章把它當成一個完整的問題來處理。

System model：資源怎麼被使用

  • 系統裡有好幾種資源 resource type R1、R2、…、Rm，例如 CPU cycle、記憶體空間、I/O 裝置。
  • 每種資源 Ri 有 Wi 個 instance。例如系統有 4 顆 CPU，CPU 這種資源就有 4 個 instance。

正常情況下，thread 用資源一定照這個順序：

  1. Request：要求資源。如果沒辦法馬上給，thread 就要等，例如要的 mutex 正被別的 thread 拿著。
  2. Use：使用資源，例如拿到 mutex 之後進入 critical section。
  3. Release：用完釋放資源。

四個必要條件

下面四個條件同時成立才會有 deadlock。反過來說，只要破壞其中任何一個，就不會 deadlock。

Mutual exclusion（互斥）
資源同一時間只能給一個人用。
Hold and wait（持有並等待）
有人手上拿著一些資源，同時又在等別的資源。
No preemption（不可搶奪）
資源只能由拿著它的 process 做完工作後自願釋放，別人不能搶走。
Circular wait（循環等待）
存在一組 {T0, T1, …, Tn}：T0 在等 T1 手上的資源、T1 在等 T2 手上的資源、…、Tn 在等 T0 手上的資源，繞成一圈。

用窄橋的例子對照：橋上一段路只能有一台車（mutual exclusion）；兩台車都佔著自己那半座橋又要對方那半（hold and wait）；不能用吊車把車吊走（no preemption）；A 等 B、B 等 A（circular wait）。

Resource-allocation graph

Resource-allocation graph（資源配置圖，簡稱 RAG）用一張有向圖描述現在誰拿著什麼、誰在等什麼。點有兩種：

  • T = {T1, T2, …, Tn}：系統裡所有的 thread，畫成圓圈。
  • R = {R1, R2, …, Rm}：系統裡所有的資源種類，畫成方框，方框裡的點代表有幾個 instance。

邊也有兩種：

Request edge：Ti → Rj
Ti 要求了 Rj 的一個 instance，正在等。
Assignment edge：Rj → Ti
Rj 的一個 instance 已經配給 Ti，Ti 正拿著它。

從圖上判斷的基本規則：

  • 沒有 cycle：一定沒有 deadlock，因為 circular wait 不可能成立。
  • 有 cycle，而且每種資源只有一個 instance：一定 deadlock。
  • 有 cycle，但資源有好幾個 instance：只是「可能」deadlock，要再看下去。
記憶技巧

看圖的觀察重點：先找出有在等資源的 thread，再一個一個評估它「有沒有可能等到」。如果有某個 thread 沒在等任何東西，它做完就會釋放資源，等它的人就有機會等到。全部的人都在等這群裡的其他人，才是 deadlock。

處理 deadlock 的四種方式

  • 直接忽略：假裝 deadlock 不會發生。這是包括 Linux 和 Windows 在內大多數作業系統的做法，因為 deadlock 不常發生，而預防或偵測的成本很高，真的卡住就交給開發者或使用者處理。
  • Deadlock prevention（預防）：事先防範，保證四個必要條件裡至少有一個不會成立。
  • Deadlock avoidance（避免）：邊走邊看邊閃，每次配置資源前動態檢查配置後的狀態，可能出事就不給。
  • Deadlock detection 加 recovery（偵測與復原）：允許 deadlock 發生，之後偵測出來再復原。

Deadlock prevention：破壞四個條件

想法很直接：四個條件少一個就不會 deadlock，那就從制度上讓其中一個不可能成立。

  • 破壞 mutual exclusion：把資源改成可以共用，例如唯讀的檔案可以讓很多人同時讀。但不是每種資源都辦得到，像 mutex lock 本來就不能讓好幾個 thread 同時拿著，所以這條通常破不了。
  • 破壞 hold and wait：保證 thread 要資源的時候手上沒有拿著其他資源。有兩種協定：
    • 協定一：開始執行前先一次要齊所有資源。
    • 協定二：手上沒有資源時才能要，想要新的就要先把手上的全部放掉。
    兩種都會讓資源使用率很低（很早拿到卻很晚才用），也可能 starvation（需要很多熱門資源的人一直湊不齊）。
  • 破壞 no preemption：一個 process 在等資源時，它手上已經拿著的資源隨時可以被搶走。例如 T2 拿著 R1、在等 R2，那 R1 就可以被搶過來配給在等 R1 的 T1。這只適合狀態容易保存和還原的資源，例如 CPU register 和記憶體；印表機、磁帶機這種實體資源，印到一半被搶走就沒辦法接著印，不適用。
  • 破壞 circular wait：規定所有人只能照固定的順序要資源，見下一段。這是四個裡面最實用的一個。

破壞 circular wait：資源排序

做法是幫所有資源種類 R = {R0, R1, …, RN} 編一個全域的順序，用函數 F(x) 表示資源 x 的順序號碼，規定每個 thread 只能照 F 由小到大要資源：如果 Tk 已經要過 Ri，現在想要 Rj，那一定要 F(Ri) < F(Rj)。

例子：F(SSD) = 1、F(HDD) = 5、F(printer) = 12，程式裡要資源的順序就只能是 SSD → HDD → printer，不能先拿印表機再回頭要 SSD。

為什麼這樣就不會有 circular wait？用反證法，先假設 circular wait 成立：T0 等 T1 手上的 R0、T1 等 T2 手上的 R1、…、Tn 等 T0 手上的 Rn。

  • T1 拿著 R0 又在要 R1，依規定 F(R0) < F(R1)。
  • 同理一路推下去：F(R0) < F(R1) < … < F(Rn)。
  • 但 T0 拿著 Rn 又在要 R0，所以 F(Rn) < F(R0)。
  • 合起來得到 F(R0) < F(R0)，不可能，所以 circular wait 不會成立。
補充

投影片的課後閱讀問到：如果鎖是在執行時動態取得的（例如依參數決定要鎖哪兩個帳戶），為什麼排好順序也不保證能預防 deadlock？可以讀課本 P.353 至 P.354 的說明。

Deadlock avoidance 和 prevention 的差別

  • Prevention：限制「要資源的方式」，例如只能照順序要、一次要齊。不管現在狀況如何，規則都一樣。
  • Avoidance：需要額外資訊，知道每個 thread 未來最多會怎麼要資源；每次有人要資源時，先模擬給了之後會不會有危險，覺得可能 deadlock 就拒絕這次請求。

avoidance 依資源的 instance 數有兩種做法：

  • 每種資源只有一個 instance：用 resource-allocation graph algorithm，檢查會不會形成 cycle。
  • 每種資源有好幾個 instance：用 banker's algorithm，檢查是否存在 safe sequence。

Safe state

系統處於 safe state（安全狀態），是指存在至少一種資源配置的次序，可以滿足所有 thread 的需求。這個次序叫做 safe sequence。

正式一點：存在一個次序 <T1, T2, …, Tn>，對其中每一個 Ti，它還需要的資源都能用「現在沒人用的資源」加上「排在它前面的 Tj（j < i）做完後釋放的資源」來滿足。前者是現在就能滿足，後者是未來可以滿足。

  • 不在 safe state，就叫 unsafe state。
  • Deadlock 一定在 unsafe state 裡，但在 unsafe state 不一定會 deadlock，因為 thread 不一定真的會要到 Max 那麼多。
  • 只要一直待在 safe state，就一定不會 deadlock。所以 avoidance 的規則是：只有配置後系統仍在 safe state，才答應這次請求。

生活例子：銀行手上的現金不夠一次借給所有客戶，但只要能排出一個順序，讓每個客戶依序借到他宣告的上限、還錢之後再借給下一個，銀行就是安全的。

Resource-allocation graph algorithm

給每種資源只有一個 instance 的系統用。在 RAG 上多加一種邊：

Claim edge：Ti - - > Rj（虛線）
Ti 未來可能會要求 Rj。每個 thread 開始執行前，就要把所有 claim edge 先畫好。
  • Ti 真的要求 Rj 時，claim edge 變成 request edge。
  • Ti 釋放 Rj 時，assignment edge 變回 claim edge。
  • 只有在「把這條 request edge 轉成 assignment edge 之後，圖上不會出現 cycle」時，才答應這次請求。直覺意義是：如果未來 R 配給 T 之後會形成 cycle，現在就不給。

它的限制：

  • 只能用在每種資源只有一個 instance 的情況。
  • 資源需求要事先宣告（claim edge 要先畫好），不能臨時多要。
  • 用 RAG 檢查 cycle 的時間是 O(n²)，n 是系統裡的 thread 數。

Banker's algorithm

資源有好幾個 instance 時，cycle 不代表一定 deadlock，就改用 banker's algorithm（銀行家演算法）。它是一個通用的安全檢查：每次配置之前，先模擬配置後還找不找得到 safe sequence，找得到才真的配置。

設 n 是 process 數、m 是資源種類數，需要四個資料結構：

Available（長度 m 的向量）
Available[j] = k 代表資源 Rj 現在還有 k 個 instance 可以用。
Max（n × m 矩陣）
Max[i][j] = k 代表 Pi 最多會要 k 個 Rj，要事先宣告。
Allocation（n × m 矩陣）
Allocation[i][j] = k 代表 Pi 現在拿著 k 個 Rj。
Need（n × m 矩陣）
Need[i][j] = k 代表 Pi 還可能需要 k 個 Rj 才能做完。Need = Max − Allocation。

它由兩個部分組成：

  • Safety algorithm：判斷目前狀態是不是 safe。假設每個 process 都會要到 Max，找一個用現有資源就能滿足 Need 的 process，讓它做完並歸還資源，再回去找下一個，直到全部滿足（safe）或找不到人（unsafe）。
  • Resource-request algorithm：Pi 送出請求 Request_i 時，先檢查不能超過自己宣告的 Need、也不能超過 Available，再假裝配置下去並跑 safety algorithm。safe 就真的配置；unsafe 就讓 Pi 等，並把狀態還原。

為什麼叫銀行家？銀行不會把錢借到「就算所有客戶都照上限來借，也沒辦法依某個順序全部滿足」的程度。

Deadlock detection：單一 instance

如果不做 prevention 也不做 avoidance，就要能偵測 deadlock。每種資源只有一個 instance 時，把 RAG 簡化成 wait-for graph（等待圖）：

  • 點只剩 process，把資源的點拿掉。
  • Pi → Pj 代表 Pi 在等 Pj 手上的資源（原本是 Pi → R → Pj 兩條邊）。
  • 定期呼叫演算法在圖上找 cycle，有 cycle 就有 deadlock。

Deadlock detection：好幾個 instance

資源有好幾個 instance 時，用和 safety algorithm 很像的偵測演算法，資料結構有 Available、Allocation，以及：

Request（n × m 矩陣）
Request[i][j] = k 代表 Pi 現在正在要求 k 個 Rj。

和 safety algorithm 的兩個差別：

  • 比的是 Request（現在真的在要的），不是 Need（未來最多可能要的）。偵測只關心「現在是不是已經卡死」，所以樂觀地假設拿到這次要的東西就能做完。
  • 一開始手上沒有任何資源（Allocation 全是 0）的 process，Finish 直接設成 true，因為它不可能卡住別人。

最後 Finish[i] 還是 false 的 Pi，就是陷入 deadlock 的 process。

Deadlock recovery

偵測到 deadlock 之後，有兩類復原方法：

  • Process termination（終止 process）：
    • 把所有 deadlock 的 process 全部終止：一定能解開，但代價大，大家做到一半的工作都白費。
    • 一次終止一個，直到 cycle 解開：每殺一個都要重跑一次偵測，而且要決定先殺誰，原則是挑代價最小的。
  • Resource preemption（搶資源）：
    • 選 victim：要搶誰的資源？要考慮的因素很多，見課本 P.366 至 P.367。
    • Rollback：被搶的 process 要退回某個安全的狀態，再從那裡重新開始。可以只退一部分（partial rollback），也可以整個重來（total rollback）。
    • Starvation：要確保不會一直挑同一個 process 當 victim，例如把被 rollback 的次數也算進代價裡。

實際例子

看 resource-allocation graph 判斷 deadlock

投影片上的系統：R1 有 1 個 instance、R2 有 2 個、R3 有 1 個、R4 有 3 個。邊的集合是 E = {T1 → R1, T2 → R3, R1 → T2, R2 → T2, R2 → T1, R3 → T3}，也就是：

  • T1 拿著一個 R2，在等 R1。
  • T2 拿著 R1 和一個 R2，在等 R3。
  • T3 拿著 R3。

這時候圖上沒有 cycle，T3 沒在等任何東西，做完就會放掉 R3，T2 接著拿到 R3，再放掉 R1 給 T1，所以沒有 deadlock。

Case 1：T3 再要求一個 R2（下圖虛線）：

 T1 ──request──▶ R1 [●] ──assign──▶ T2 ──request──▶ R3 [●] ──assign──▶ T3
 ▲                                  ▲                                  ┊
 │                                  │                                  ┊ Case 1
 └──assign──── R2 [● ●] ───assign───┘                                  ┊ request
                ▲                                                      ┊
                └┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┘

 R4 [● ● ●]

出現兩個最小的 cycle：

  • T1 → R1 → T2 → R3 → T3 → R2 → T1
  • T2 → R3 → T3 → R2 → T2

R2 雖然有 2 個 instance，但兩個都被 T1、T2 拿著，而 T1 在等 T2、T2 在等 T3、T3 在等 T1 或 T2 放掉 R2。三個 thread 都在等這群裡的其他人，deadlock。

Case 2：另一張圖，R1、R2 各有 2 個 instance：

 T2 ◀──assign── R1 [● ●] ◀──request── T1
                 │                    ▲
                 │ assign             │ assign
                 ▼                    │
                T3 ──request───────▶ R2 [● ●] ──assign──▶ T4

圖上有 cycle：T1 → R1 → T3 → R2 → T1。但是 T2 和 T4 沒有在等任何東西：

  • T4 做完會釋放它的 R2，T3 就能拿到 R2。
  • T2 做完會釋放它的 R1，T1 就能拿到 R1。

所以有 cycle 但沒有 deadlock。這就是「資源有好幾個 instance 時，cycle 只代表可能 deadlock」的意思。

兩把 mutex 的 deadlock 與 wait-for graph

T1 先拿 first_mutex 再拿 second_mutex；T2 反過來，先拿 second_mutex 再拿 first_mutex。如果 T1 拿到 first_mutex、T2 拿到 second_mutex，兩邊就會互相等：

 T1 ──request──▶ second_mutex ──assign──▶ T2
 ▲                                         │
 └──assign─── first_mutex ◀──request───────┘

 wait-for graph：T1 ──▶ T2 ──▶ T1

兩把 mutex 都只有一個 instance，把資源的點拿掉，就得到 wait-for graph：T1 在等 T2、T2 在等 T1，有 cycle，所以 deadlock。

修正方法就是資源排序：讓 T2 也改成先要 first_mutex 再要 second_mutex。這樣 T1、T2 只會有一個人先搶到 first_mutex，另一個在第一步就等，不會拿著東西等。

#include <stdio.h>
#include <pthread.h>
#include <unistd.h>

pthread_mutex_t first_mutex = PTHREAD_MUTEX_INITIALIZER;
pthread_mutex_t second_mutex = PTHREAD_MUTEX_INITIALIZER;

void *do_work_one(void *arg) {
    pthread_mutex_lock(&first_mutex);
    printf("thread one got first_mutex\n");
    sleep(1);                              // 故意停一下，讓 thread two 拿到 second_mutex
    pthread_mutex_lock(&second_mutex);
    printf("thread one got second_mutex\n");
    pthread_mutex_unlock(&second_mutex);
    pthread_mutex_unlock(&first_mutex);
    return NULL;
}

void *do_work_two(void *arg) {
    pthread_mutex_lock(&second_mutex);     // 順序和 thread one 相反
    printf("thread two got second_mutex\n");
    sleep(1);
    pthread_mutex_lock(&first_mutex);
    printf("thread two got first_mutex\n");
    pthread_mutex_unlock(&first_mutex);
    pthread_mutex_unlock(&second_mutex);
    return NULL;
}

int main(void) {
    setvbuf(stdout, NULL, _IONBF, 0);      // 不緩衝，卡住前印的字才看得到
    pthread_t t1, t2;
    pthread_create(&t1, NULL, do_work_one, NULL);
    pthread_create(&t2, NULL, do_work_two, NULL);
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
    printf("done\n");
    return 0;
}

編譯：gcc deadlock.c -o deadlock -pthread

thread two got second_mutex

  • T0 還需要 10 − 5 = 5 個，大於 4，給不起。
  • T2 還需要 9 − 3 = 6 個，大於 4，也給不起。

兩條路都不通，找不到 safe sequence，這次配置會讓系統進入 unsafe state。所以 avoidance 不會答應 T2 這次的請求，T2 要先等。

Banker's algorithm：安全檢查

5 個 process、3 種資源，總數 A = 10、B = 5、C = 7。目前已用 A = 7、B = 2、C = 5，所以 Available = (3, 3, 2)。先算出 Need = Max − Allocation：

從 Work = Available = (3, 3, 2) 開始，每次找一個 Need ≤ Work 的 process，讓它做完並把 Allocation 還回來：

全部的 process 都能做完，safe sequence 是 <P1, P3, P4, P2, P0>，系統在 safe state。最後的 Work 等於資源總數 (10, 5, 7)，可以拿來驗算。

補充

safe sequence 不一定只有一種。例如第 3 步時 Work = (7, 4, 3)，P0 的 Need (7, 4, 3) 也剛好給得起，先選 P0 也可以。考試只要找到一組、而且每一步都驗算正確就是 safe。

Banker's algorithm：處理請求

情況一：P1 請求 (1, 0, 2)

  1. Request ≤ Need：(1, 0, 2) ≤ (1, 2, 2)，沒有超過宣告。
  2. Request ≤ Available：(1, 0, 2) ≤ (3, 3, 2)，現在給得起。
  3. 假裝配置：Available 變成 (2, 3, 0)，P1 的 Allocation 變成 (3, 0, 2)，Need 變成 (0, 2, 0)。
  4. 跑 safety algorithm：
步驟選誰Work（之前）NeedWork（之後）
1P12 3 00 2 05 3 2
2P35 3 20 1 17 4 3
3P47 4 34 3 17 4 5
4P07 4 57 4 37 5 5
5P27 5 56 0 010 5 7

找得到 safe sequence <P1, P3, P4, P0, P2>，進入另一個 safe state，所以答應 P1 的請求。

情況二：P4 請求 (3, 3, 0)（回到原本 Available = (3, 3, 2) 的狀態）

  1. Request ≤ Need：(3, 3, 0) ≤ (4, 3, 1)，沒問題。
  2. Request ≤ Available：(3, 3, 0) ≤ (3, 3, 2)，給得起。
  3. 假裝配置：Available 變成 (0, 0, 2)，P4 的 Allocation 變成 (3, 3, 2)，Need 變成 (1, 0, 1)。
  4. 跑 safety algorithm：P0 要 (7, 4, 3)、P1 要 (1, 2, 2)、P2 要 (6, 0, 0)、P3 要 (0, 1, 1)、P4 要 (1, 0, 1)，每一個都至少有一項大於 (0, 0, 2)，一個都給不起。

找不到 safe sequence，會進入 unsafe state，所以拒絕，P4 要等，狀態還原。注意這次請求在第 2 步明明「給得起」，但 banker's algorithm 還是不給，這就是 avoidance 和單純檢查有沒有庫存的差別。

Deadlock detection：好幾個 instance

5 個 process、3 種資源，總數 A = 7、B = 2、C = 6，而且 Available = (0, 0, 0)，資源全被拿走了：

ProcessAllocation（A B C）Request（A B C）
P00 1 00 0 0
P12 0 02 0 2
P23 0 30 0 0
P32 1 11 0 0
P40 0 20 0 2

每個 process 都拿著資源，所以 Finish 一開始全是 false。從 Work = (0, 0, 0) 開始，找 Request ≤ Work 的 process：

步驟選誰Work（之前）RequestWork（之後）
1P00 0 00 0 00 1 0
2P20 1 00 0 03 1 3
3P33 1 31 0 05 2 4
4P15 2 42 0 27 2 4
5P47 2 40 0 27 2 6

<P0, P2, P3, P1, P4> 全部都能完成，沒有 deadlock。

如果 P2 多要求一個 C，Request(P2) 變成 (0, 0, 1)：

  • P0 的 Request 是 (0, 0, 0)，可以完成，歸還後 Work = (0, 1, 0)。
  • P1 要 (2, 0, 2)、P2 要 (0, 0, 1)、P3 要 (1, 0, 0)、P4 要 (0, 0, 2)，A 和 C 都是 0，一個都滿足不了。

能收回的只有 P0 那一個 B，不夠滿足其他人的請求，所以 P1、P2、P3、P4 陷入 deadlock。

Pseudocode

Safety algorithm

// n 個 process、m 種資源
// need[i][j] = max[i][j] - allocation[i][j]
FUNCTION is_safe(available, allocation, need)
    work = copy(available)              // 長度 m
    FOR i = 0 TO n - 1
        finish[i] = false
    END FOR

    WHILE true
        found = false
        FOR i = 0 TO n - 1
            IF finish[i] == false AND need[i] <= work THEN   // 每一項都要 <=
                work = work + allocation[i]   // 假設 Pi 做完，歸還它拿著的資源
                finish[i] = true
                found = true
            END IF
        END FOR
        IF found == false THEN
            BREAK                          // 找不到任何人可以做完
        END IF
    END WHILE

    IF finish[i] == true FOR ALL i THEN
        RETURN true                        // safe state
    END IF
    RETURN false                           // unsafe state
END FUNCTION

Resource-request algorithm

// Pi 送出請求 request_i（長度 m）
FUNCTION request_resources(i, request_i)
    IF NOT (request_i <= need[i]) THEN
        RETURN error                       // 超過自己宣告的最大需求
    END IF
    IF NOT (request_i <= available) THEN
        block(Pi)                          // 資源不夠，Pi 必須等
        RETURN
    END IF

    // 假裝配置下去
    available     = available - request_i
    allocation[i] = allocation[i] + request_i
    need[i]       = need[i] - request_i

    IF is_safe(available, allocation, need) THEN
        RETURN granted                     // 真的配置給 Pi
    ELSE
        // 還原成配置前的狀態，Pi 必須等
        available     = available + request_i
        allocation[i] = allocation[i] - request_i
        need[i]       = need[i] + request_i
        block(Pi)
    END IF
END FUNCTION

Detection algorithm（好幾個 instance）

FUNCTION detect_deadlock(available, allocation, request)
    work = copy(available)
    FOR i = 0 TO n - 1
        IF allocation[i] != 0 THEN
            finish[i] = false
        ELSE
            finish[i] = true               // 手上沒資源，不可能卡住別人
        END IF
    END FOR

    WHILE EXISTS i WHERE finish[i] == false AND request[i] <= work
        work = work + allocation[i]        // 樂觀假設 Pi 拿到這次要的就能做完
        finish[i] = true
    END WHILE

    deadlocked = []
    FOR i = 0 TO n - 1
        IF finish[i] == false THEN
            deadlocked.add(Pi)             // Pi 陷入 deadlock
        END IF
    END FOR
    RETURN deadlocked                      // 空的就代表沒有 deadlock
END FUNCTION

用資源排序預防 circular wait

// 每種資源有固定的順序號碼 F(r)，例如 F(first_mutex) = 1、F(second_mutex) = 2
FUNCTION acquire_all(resources)
    sort(resources, key = F)               // 依順序號碼由小到大排
    FOR EACH r IN resources
        acquire(r)                         // 一律照順序拿，不能回頭拿號碼小的
    END FOR
END FUNCTION

// T1 和 T2 都照同一個順序
acquire_all([first_mutex, second_mutex])
// critical section
release(second_mutex)
release(first_mutex)

比較整理

方式做法優點缺點適用情境
直接忽略當作不會發生沒有額外成本真的卡住只能人工處理deadlock 很少發生的一般作業系統，例如 Linux、Windows
Prevention事先防範，破壞四個必要條件之一保證不會 deadlock，不用執行期檢查資源使用率低、可能 starvation，有些條件破不了能規定資源取得方式的情境，例如固定上鎖順序
Avoidance邊走邊看邊閃，配置後仍是 safe state 才答應比 prevention 有彈性，資源使用率較高要事先知道最大需求，每次配置都要跑檢查process 數和最大需求能事先宣告的系統

自我測驗

Q1. Resource-allocation graph 上有 cycle，系統一定 deadlock 嗎？

答案：不一定。每種資源只有一個 instance 時一定 deadlock；有好幾個 instance 時只是可能 deadlock。

原因：資源有好幾個 instance 時，cycle 外面可能有沒在等東西的 thread 拿著同一種資源，它做完釋放後，cycle 裡在等的人就能拿到，cycle 自然解開。例如 Case 2 裡 T2、T4 不在等任何東西，做完之後 T1、T3 都能拿到資源。

Q2. 為什麼「所有資源排順序、只能由小到大要」就不會有 circular wait？

答案：因為 circular wait 需要順序號碼繞一圈回到自己，排序規則讓這件事不可能。

原因：假設 T0 → T1 → … → Tn → T0 形成循環等待，每個 thread 都拿著前一個資源在要下一個，依規定 F(R0) < F(R1) < … < F(Rn) < F(R0)，推出 F(R0) < F(R0)，矛盾，所以假設不成立。

Q3. Unsafe state 一定會 deadlock 嗎？那 avoidance 為什麼要避開所有 unsafe state？

答案：不一定會 deadlock，但 deadlock 一定在 unsafe state 裡，所以只要一直待在 safe state 就保證不會 deadlock。

原因：safety 檢查假設每個 thread 都會要到 Max，這是最壞情況。實際上 thread 可能不會要那麼多，或先釋放一些資源，所以 unsafe 不代表一定卡死。但 OS 沒辦法預知實際情況，只能保守地避開所有「有可能」卡死的狀態。

Q4. 在 banker's algorithm 的例子裡，P4 請求 (3, 3, 0) 時 Available 是 (3, 3, 2)，明明給得起，為什麼要拒絕？

答案：因為給了之後 Available 變成 (0, 0, 2)，找不到 safe sequence，系統會進入 unsafe state。

原因：banker's algorithm 不只看「現在有沒有庫存」，還要假裝配置後跑 safety algorithm。配置後每個 process 的 Need 都至少有一項大於 (0, 0, 2)，沒有人能保證做完歸還資源，所以這次請求要讓 P4 等，狀態還原。

Q5. Detection algorithm 和 banker's 的 safety algorithm 長得很像，差在哪裡？

答案：detection 比的是 Request（現在正在要的），safety 比的是 Need（未來最多可能要的）；另外 detection 會把手上沒資源的 process 一開始就設成 Finish = true。

原因：avoidance 要預防未來可能出事，所以照最壞情況 Need 去算；detection 只想知道現在是不是已經卡死，所以只看現在的 Request，樂觀假設拿到就能做完。手上沒有資源的 process 不會讓任何人等它，不可能是 deadlock 的一部分。

Q6. 用 resource preemption 復原 deadlock 時，為什麼要擔心 starvation？

答案：因為如果選 victim 只看代價，可能每次都挑同一個 process，它就一直被搶、一直 rollback，永遠做不完。

原因：選 victim 通常挑代價最小的，同一個 process 很可能每次都是代價最小的那個。常見的做法是把被 rollback 的次數也算進代價，被選過越多次越不容易再被選中。

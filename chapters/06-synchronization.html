CHAPTER 06

同步工具

Synchronization Tools

本章重點

  • 多個 process / thread 同時改同一份資料，結果取決於執行順序，這叫 race condition，連 kernel 裡的變數都會發生。
  • 會碰到共用資料的那段程式叫 critical section，解法要滿足 mutual exclusion、progress、bounded waiting。
  • 軟體解法：強制輪流法缺 progress；Peterson's solution 三個條件都滿足，但現代 CPU 會重排指令，需要 memory barrier。
  • 硬體支援：memory barrier、test_and_set、compare_and_swap（CAS），以及用 CAS 做出的 atomic variable。
  • 給一般開發者用的高階工具是 mutex lock（通常實作成 spinlock），POSIX 用 pthread_mutex；semaphore 是下一份投影片的內容。

核心觀念

Race condition

一行 counter++ 看起來是一個動作，但 CPU 其實要做三步：

register = counter        // 1. 從記憶體讀出來
register = register + 1   // 2. 在暫存器裡加一
counter  = register       // 3. 寫回記憶體

如果兩個 thread 同時做 counter++，三個步驟可能交錯執行，其中一次的加法就被「蓋掉」了。這種「結果取決於誰先誰後」的情況叫做 race condition（競爭狀況）。

生活例子：你和室友共用一個記帳 App，餘額 500。你記一筆 +100，他同時記一筆 +200。如果兩支手機都先讀到 500，你寫回 600，他寫回 700，最後餘額變成 700，你那筆 100 就不見了。

Kernel 裡的 race condition

race condition 不只發生在使用者程式。例如 P0 和 P1 同時呼叫 fork()，kernel 都要讀取變數 next_available_pid（下一個可用的 pid）。如果沒有互斥，兩個新 process 可能拿到同一個 pid，這顯然不合理。

單核心時可以暫時關掉 interrupt，讓手上的指令一口氣做完；但多核心時其他 CPU 照樣在跑、照樣能存取 shared memory，所以沒用。kernel 處理 critical section 有兩種方式：

  • Non-preemptive kernel：在 kernel mode 執行的 process 不會被搶走，直到它離開 kernel、block 或主動讓出 CPU，所以 kernel 資料不會有 race condition。
  • Preemptive kernel：允許在 kernel mode 被搶，回應比較快、適合即時系統，但設計時要非常小心。

Critical section 的三個必要條件

會讀寫共用資料的那段程式叫 critical section（臨界區）。任何解法都要滿足：

Mutual exclusion（互斥）
同一時間最多只有一個 thread 在 critical section 裡面。
Progress（進行）
如果 critical section 沒人在用，又有人想進去，那就必須能在有限時間內決定讓誰進去，不能大家卡住。而且只有想進去的人能參與決定。
Bounded waiting（有限等待）
一個 thread 提出要進去之後，別人插隊的次數有上限，不會永遠等不到。
記憶技巧

想成一間單人廁所：一次只能一個人（mutual exclusion）、沒人在用時想上的人要能進去（progress）、排隊的人不會一直被插隊（bounded waiting）。

Critical section 的程式結構

WHILE true
    entry section          // 申請進入：表達意願、等待許可
        critical section   // 存取共用資料
    exit section           // 離開時通知別人
        remainder section  // 其他不相關的程式
END WHILE

解法要設計的就是 entry section 和 exit section。注意：process 離開 remainder、進入 entry section，才代表「有意願」進 critical section。

先試試：強制輪流法

只有兩個 process P0 和 P1，共用一個變數 turn 表示現在誰有權利進 critical section。Pi 等到 turn == i 才進去，出來時把 turn 交給對方。

結果：mutual exclusion 有滿足（turn 同時只會是一個值）、bounded waiting 有滿足（嚴格輪流，不會被插隊），但 progress 不滿足。如果 P0 上次出來後一直留在 remainder，P1 用完一次後就要一直等 turn 回到自己身上，但 critical section 明明沒人在用。就算有權利，沒有意願也不該佔著不放。

解法一：Peterson's solution（純軟體）

兩個 thread 共用兩個變數：flag[i] 表示「我想進去」，turn 表示「現在禮讓誰」。想進去時先舉手，再把 turn 讓給對方；只有在「對方也想進去而且輪到對方」時才等待。

為什麼要這樣設計：

  • 只用 turn 嚴格輪流：對方不想進去時我也進不去，違反 progress。
  • 只用 flag：兩個人同時舉手就會互相等，卡死。
  • Peterson 把兩個合起來，三個條件都滿足。
常見錯誤

Peterson's solution 在現代 CPU 上不保證正確，因為 CPU 和編譯器可能為了效能重新排列記憶體讀寫順序。它在課本裡的價值是幫助理解三個條件，實務上要靠硬體支援的 atomic 指令或 memory barrier。

指令重排與 Memory barrier

Peterson's solution 有兩個限制：

  • 只能用在兩個 process。
  • 現代 CPU 和編譯器為了效能（例如避免 pipeline stall）可能重排沒有相依關係的指令，讓它失效。

看這個例子，兩個 thread 共用 flag = false 和 x = 0：

/* Thread 1 */                    /* Thread 2 */
while (!flag)                     x = 100;
    ;                             flag = true;
print x;

我們期待印出 100。但 Thread 2 的兩行彼此沒有相依，可能被重排成先 flag = true 再 x = 100，Thread 1 就可能印出 0。

解法是 memory barrier（memory fence）：一道指令，強制在它之前的所有 load 和 store 都完成、並讓其他處理器看得到，才執行之後的指令。在 Thread 2 的兩行中間加 memory_barrier()，就保證 x 先寫入、flag 才設成 true；Thread 1 在 while 之後加，保證先讀 flag 再讀 x。

解法二：硬體指令 test_and_set

硬體提供一個 atomic（不可分割）的指令：讀出舊值並寫入 true，這兩件事中間不可能被打斷。用它就能做出 spinlock：一直嘗試，直到拿到鎖為止。它解決了 Peterson 只能用在兩個 thread、而且怕重排的問題。

缺點是 busy waiting：等的人會一直在迴圈裡空轉，浪費 CPU。在單核 CPU 上更糟，因為拿著鎖的人沒辦法在你空轉時執行。

compare_and_swap 與 Atomic variable

Atomic operation 是指一個操作要嘛完全執行、要嘛完全不執行，不會出現做一半的狀態，像原子一樣不可分割。硬體提供的另一個 atomic 指令是 compare_and_swap（CAS）：如果記憶體裡的值等於預期值，就換成新值；不管有沒有換，都回傳原本的值。

用 CAS 可以做出 atomic variable，例如 atomic 的 increment()：先讀出目前的值，再用 CAS 嘗試把它加一；如果這段時間被別人改過，CAS 會失敗，就重讀再試一次。這樣 count++ 不需要上鎖也不會有 race condition。

單純用 CAS 做的鎖滿足 mutual exclusion，但可能有人一直搶不到。投影片的 bounded-waiting 版本加了 waiting[n] 陣列：離開 critical section 的人依序往後找下一個正在等的 process，直接把它放行（把它的 waiting 設成 false）；找不到才把 lock 解開。這樣任何人最多等 n − 1 輪。

解法三：Mutex lock

一般開發者不會直接用上面那些硬體指令，而是用 OS 提供的高階工具。Mutex lock（mutual exclusion）用一個 boolean 變數 available 表示鎖能不能拿，進 critical section 前 acquire()、出來後 release()。這兩個呼叫本身必須是 atomic，用前面的硬體指令實作。

課本版本的 acquire() 拿不到鎖就一直在迴圈裡等，也就是 busy waiting，這種鎖叫 spinlock（前面的 test_and_set、CAS 鎖都是）。它浪費 CPU，但不用 context switch，省下切換的時間，所以適合 critical section 一次只會被佔用一小段時間的情況，在多核心電腦上被大量使用：核心多，暫時被佔用一兩顆也不怕。

POSIX 提供的是 pthread_mutex_t：用 pthread_mutex_init 建立、pthread_mutex_lock 取得、pthread_mutex_unlock 釋放（見「實際例子」）。

補充

實際函式庫的 mutex 常是混合式：先 spin 一小段時間，還拿不到才讓 thread 去睡（進入 waiting、讓出 CPU）。細節依作業系統和函式庫實作而異。

解法四：Semaphore

補充

依上課進度，semaphore 和下面的 bounded buffer 會在下一份投影片（Synchronization Examples）詳細介紹，這裡先整理概念。

semaphore（號誌）是一個整數 S，只能用兩個 atomic 操作去改：

  • wait(S)（也寫作 P 或 down）：S 減一，如果變成負數就去睡。
  • signal(S)（也寫作 V 或 up）：S 加一，如果有人在睡就叫醒一個。

可以把 S 想成停車場的空位數：開進去前先 wait，沒位子就在門口等；開出來時 signal，讓門口的車進來。

Binary semaphore
初始值 1，只會是 0 或 1，用法跟 mutex 一樣。
Counting semaphore
初始值 N，代表有 N 份資源可以同時給 N 個人用。

semaphore 比 mutex 更通用的地方是它還能拿來「排順序」：把 S 初始為 0，A 做完後 signal(S)，B 開始前 wait(S)，就能保證 B 一定在 A 之後。

實際例子

手動追蹤 race condition

counter 一開始是 5，T1 和 T2 各做一次 counter++，正確答案應該是 7。看看下面這種交錯：

時間T1T2counter
1reg1 = counter（5）5
2reg1 = reg1 + 1（6）5
3context switch 到 T25
4reg2 = counter（5）5
5reg2 = reg2 + 1（6）5
6counter = reg26
7counter = reg16

最後是 6 不是 7。問題在 T2 讀到的是 T1 還沒寫回去的舊值。

用 pthread 實際跑一次

#include <stdio.h>
#include <pthread.h>

#define N 1000000

long counter = 0;
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;

void *worker(void *arg) {
    for (int i = 0; i < N; i++) {
        pthread_mutex_lock(&lock);     // 把這行和 unlock 拿掉就會出現 race condition
        counter++;
        pthread_mutex_unlock(&lock);
    }
    return NULL;
}

int main(void) {
    pthread_t t1, t2;
    pthread_create(&t1, NULL, worker, NULL);
    pthread_create(&t2, NULL, worker, NULL);
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
    printf("counter = %ld (expected %d)\n", counter, 2 * N);
    return 0;
}

編譯：gcc race.c -o race -pthread

  • 有加鎖：每次都印 counter = 2000000 (expected 2000000)。
  • 拿掉鎖：多核心電腦上通常會印出小於 2000000 的數字，而且每次跑都不一樣，這就是 race condition 的特徵。

指令重排會讓結果變怎樣？

延續「核心觀念」裡 flag 和 x 的例子，Thread 2 的指令可能有兩種執行順序：

Thread 2 實際執行的順序Thread 1 印出說明
x = 100 → flag = true100照程式順序，正確
flag = true → x = 1000 或 100Thread 1 看到 flag 變 true 時，x 可能還沒寫入，結果看誰先執行，就是 race condition

在 Thread 2 的兩行中間加上 memory barrier 後，只剩第一種順序，一定印出 100。

Pseudocode

Peterson's solution（thread i，對方是 j = 1 − i）

// 共用變數
flag[2] = {false, false}
turn = 0

WHILE true
    flag[i] = true            // 我想進去
    turn = j                  // 先禮讓對方
    WHILE flag[j] AND turn == j
        // busy wait：對方想進去而且輪到對方，我就等
    END WHILE

    // ===== critical section =====

    flag[i] = false           // 我出來了
    // remainder section
END WHILE

test_and_set spinlock

// 硬體保證整個函式是 atomic
FUNCTION test_and_set(target)
    old = *target
    *target = true
    RETURN old
END FUNCTION

lock = false

FUNCTION acquire()
    WHILE test_and_set(&lock) == true
        // 拿到的舊值是 true，代表別人拿著鎖，繼續轉
    END WHILE
END FUNCTION

FUNCTION release()
    lock = false
END FUNCTION

強制輪流法（process i，對方是 j）

turn = 0                       // 共用：現在輪到誰

WHILE true
    WHILE turn != i
        // 不是我的回合，一直等
    END WHILE
    // ===== critical section =====
    turn = j                   // 把權利交給對方
    // remainder section
END WHILE

compare_and_swap 與 atomic increment

// 硬體保證整個函式是 atomic
FUNCTION compare_and_swap(value, expected, new_value)
    temp = *value
    IF *value == expected THEN
        *value = new_value
    END IF
    RETURN temp                    // 永遠回傳原本的值
END FUNCTION

// 用 CAS 做 atomic variable 的加一
FUNCTION increment(v)
    DO
        temp = *v
    WHILE temp != compare_and_swap(v, temp, temp + 1)
    // 如果中間被別人改過，CAS 失敗，重讀再試
END FUNCTION

CAS + bounded waiting（n 個 process）

waiting[n] = {false, ...}      // 誰正在等
lock = 0                       // 0 = 沒鎖

WHILE true
    waiting[i] = true
    key = 1
    WHILE waiting[i] AND key == 1
        key = compare_and_swap(&lock, 0, 1)
    END WHILE
    waiting[i] = false
    // ===== critical section =====
    j = (i + 1) % n
    WHILE j != i AND NOT waiting[j]
        j = (j + 1) % n            // 依序找下一個正在等的人
    END WHILE
    IF j == i THEN
        lock = 0                   // 沒人在等，解鎖
    ELSE
        waiting[j] = false         // 直接放行下一個人
    END IF
    // remainder section
END WHILE

Mutex lock（課本的 spinlock 版本）

available = true

FUNCTION acquire()             // 整個函式必須是 atomic
    WHILE NOT available
        // busy waiting
    END WHILE
    available = false
END FUNCTION

FUNCTION release()
    available = true
END FUNCTION

Semaphore（不 busy waiting 的版本）

// S.value：整數；S.list：在等這個 semaphore 的 thread
FUNCTION wait(S)
    S.value = S.value - 1
    IF S.value < 0 THEN
        S.list.add(current_thread)
        block()               // 進入 waiting，讓出 CPU
    END IF
END FUNCTION

FUNCTION signal(S)
    S.value = S.value + 1
    IF S.value <= 0 THEN
        t = S.list.remove()
        wakeup(t)             // 把 t 移回 ready queue
    END IF
END FUNCTION
記憶技巧

S.value 是負數時，它的絕對值剛好等於「正在等的人數」。例如 S.value = −2 代表有兩個 thread 在排隊。

Bounded buffer（生產者與消費者）

// buffer 有 n 格
semaphore mutex = 1      // 保護 buffer 本身
semaphore empty = n      // 空格數
semaphore full  = 0      // 有東西的格數

// Producer
WHILE true
    item = produce()
    wait(empty)          // 先確定有空格
    wait(mutex)
    buffer.add(item)
    signal(mutex)
    signal(full)         // 多一格有東西
END WHILE

// Consumer
WHILE true
    wait(full)           // 先確定有東西
    wait(mutex)
    item = buffer.remove()
    signal(mutex)
    signal(empty)        // 多一格空格
    consume(item)
END WHILE
常見錯誤

Producer 如果寫成先 wait(mutex) 再 wait(empty)：buffer 滿的時候，它拿著 mutex 去睡覺等空格，但 consumer 要先拿到 mutex 才能拿走東西、產生空格，兩邊互相等，就 deadlock 了。原則是：先等資源，再拿鎖。

自我測驗

Q1. 兩個 thread 只用一個共用變數 turn 嚴格輪流進入 critical section（T0 進完換 T1，T1 進完換 T0），違反了哪個條件？

答案：Progress。

原因：如果現在 turn = 1，但 T1 根本不想進去，T0 想進去卻只能一直等。critical section 明明沒人用，卻不能讓想進去的人進去，就是違反 progress。mutual exclusion 倒是有滿足。

Q2. 一台印表機伺服器有 3 台印表機，要用 semaphore 控制同時使用的人數，初始值要設多少？第 5 個人呼叫 wait 後 S.value 是多少？

答案：初始值 3；第 5 個人呼叫 wait 後 S.value = −2。

原因：counting semaphore 的初始值就是資源數量。每個 wait 減一：3 → 2 → 1 → 0 → −1 → −2。前 3 個人拿到印表機，第 4、5 個人在等，負數的絕對值 2 剛好就是等待人數。

Q3. 在 bounded buffer 裡，如果 consumer 寫成先 wait(mutex) 再 wait(full)，什麼情況下會出事？

答案：buffer 是空的時候會 deadlock。

原因：consumer 拿著 mutex 去等 full，但 producer 要放東西進 buffer 之前也要先拿 mutex，拿不到就放不進去，full 永遠不會增加。兩邊互相等對方手上的東西，就是 deadlock。和 producer 的情況是對稱的。

Q4. 為什麼在單核 CPU 上用 spinlock 通常是壞主意？

答案：因為空轉的 thread 佔著唯一的 CPU，拿著鎖的 thread 沒辦法執行去釋放鎖。

原因：spinlock 的前提是「拿著鎖的人正在別的核心上跑，很快就會放開」。單核時拿著鎖的人一定不在跑，等的人只能空轉到自己的 time slice 用完，被切換走之後持有者才有機會執行，完全是浪費。這時候用會讓出 CPU 的 mutex 比較好。

Q5. 為什麼「暫時關掉 interrupt」可以在單核心上保護 kernel 的 next_available_pid，在多核心上卻不行？

答案：關中斷只能讓自己這顆 CPU 不被打斷，其他 CPU 本來就在同時執行，還是能存取同一個變數。

原因：單核心上，別的 process 要執行一定要先透過中斷把 CPU 搶走，關掉中斷就沒人能插進來。多核心上兩個 process 可以真的同時在兩顆 CPU 上跑，根本不需要打斷你，所以要用 CAS 或 mutex 這類能跨核心的同步工具。

Q6. 用 compare_and_swap 實作的 increment() 裡，為什麼要用 do-while 迴圈？

答案：因為讀出舊值和 CAS 之間，別的 thread 可能已經改過這個變數，這時 CAS 會失敗，必須重讀再試。

原因：CAS 只有在「目前的值還等於我剛剛讀到的 temp」時才會寫入 temp + 1，並回傳原本的值。回傳值不等於 temp 代表被別人搶先改了，這次的加一沒有成功，所以用迴圈一直試到成功為止，保證每一次加一都不會被蓋掉。

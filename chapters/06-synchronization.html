CHAPTER 06

同步工具

Synchronization Tools

本章重點

  • 多個 process / thread 同時改同一份資料，結果取決於執行順序，這叫 race condition，連 kernel 裡的變數都會發生。
  • 會碰到共用資料的那段程式叫 critical section，解法要滿足 mutual exclusion、progress、bounded waiting。
  • 軟體解法：強制輪流法缺 progress；Peterson's solution 三個條件都滿足，但現代 CPU 會重排指令，需要 memory barrier。
  • 硬體支援：memory barrier、test_and_set、compare_and_swap（CAS），以及用 CAS 做出的 atomic variable；再往上一層是 mutex lock（通常實作成 spinlock）。
  • Semaphore 是管控資源的計數器，只能用 wait（P）和 signal（V）存取：大於 0 代表還有幾份資源，負數的絕對值代表有幾個人在排隊。
  • semaphore 很容易用錯，所以有更高階的 monitor：一次只讓一個 process 在裡面活動，再用 condition variable 控制誰要等、誰被叫醒；同步沒做好會出現 deadlock、priority inversion 這類 liveness 問題。

核心觀念

Race condition

一行 counter++ 看起來是一個動作，但 CPU 其實要做三步：

register = counter        // 1. 從記憶體讀出來
register = register + 1   // 2. 在暫存器裡加一
counter  = register       // 3. 寫回記憶體

如果兩個 thread 同時做 counter++，三個步驟可能交錯執行，其中一次的加法就被「蓋掉」了。這種「結果取決於誰先誰後」的情況叫做 race condition（競爭狀況）。

生活例子：你和室友共用一個記帳 App，餘額 500。你記一筆 +100，他同時記一筆 +200。如果兩支手機都先讀到 500，你寫回 600，他寫回 700，最後餘額變成 700，你那筆 100 就不見了。

Kernel 裡的 race condition

race condition 不只發生在使用者程式。例如 P0 和 P1 同時呼叫 fork()，kernel 都要讀取變數 next_available_pid（下一個可用的 pid）。如果沒有互斥，兩個新 process 可能拿到同一個 pid，這顯然不合理。

單核心時可以暫時關掉 interrupt，讓手上的指令一口氣做完；但多核心時其他 CPU 照樣在跑、照樣能存取 shared memory，所以沒用。kernel 處理 critical section 有兩種方式：

  • Non-preemptive kernel：在 kernel mode 執行的 process 不會被搶走，直到它離開 kernel、block 或主動讓出 CPU，所以 kernel 資料不會有 race condition。
  • Preemptive kernel：允許在 kernel mode 被搶，回應比較快、適合即時系統，但設計時要非常小心。

Critical section 的三個必要條件

會讀寫共用資料的那段程式叫 critical section（臨界區）。任何解法都要滿足：

Mutual exclusion（互斥）
同一時間最多只有一個 thread 在 critical section 裡面。
Progress（進行）
如果 critical section 沒人在用，又有人想進去，那就必須能在有限時間內決定讓誰進去，不能大家卡住。而且只有想進去的人能參與決定。
Bounded waiting（有限等待）
一個 thread 提出要進去之後，別人插隊的次數有上限，不會永遠等不到。
記憶技巧

想成一間單人廁所：一次只能一個人（mutual exclusion）、沒人在用時想上的人要能進去（progress）、排隊的人不會一直被插隊（bounded waiting）。

Critical section 的程式結構

WHILE true
    entry section          // 申請進入：表達意願、等待許可
        critical section   // 存取共用資料
    exit section           // 離開時通知別人
        remainder section  // 其他不相關的程式
END WHILE

解法要設計的就是 entry section 和 exit section。注意：process 離開 remainder、進入 entry section，才代表「有意願」進 critical section。

先試試：強制輪流法

只有兩個 process P0 和 P1，共用一個變數 turn 表示現在誰有權利進 critical section。Pi 等到 turn == i 才進去，出來時把 turn 交給對方。

結果：mutual exclusion 有滿足（turn 同時只會是一個值）、bounded waiting 有滿足（嚴格輪流，不會被插隊），但 progress 不滿足。如果 P0 上次出來後一直留在 remainder，P1 用完一次後就要一直等 turn 回到自己身上，但 critical section 明明沒人在用。就算有權利，沒有意願也不該佔著不放。

解法一：Peterson's solution（純軟體）

兩個 thread 共用兩個變數：flag[i] 表示「我想進去」，turn 表示「現在禮讓誰」。想進去時先舉手，再把 turn 讓給對方；只有在「對方也想進去而且輪到對方」時才等待。

為什麼要這樣設計：

  • 只用 turn 嚴格輪流：對方不想進去時我也進不去，違反 progress。
  • 只用 flag：兩個人同時舉手就會互相等，卡死。
  • Peterson 把兩個合起來，三個條件都滿足。
常見錯誤

Peterson's solution 在現代 CPU 上不保證正確，因為 CPU 和編譯器可能為了效能重新排列記憶體讀寫順序。它在課本裡的價值是幫助理解三個條件，實務上要靠硬體支援的 atomic 指令或 memory barrier。

指令重排與 Memory barrier

Peterson's solution 有兩個限制：

  • 只能用在兩個 process。
  • 現代 CPU 和編譯器為了效能（例如避免 pipeline stall）可能重排沒有相依關係的指令，讓它失效。

看這個例子，兩個 thread 共用 flag = false 和 x = 0：

/* Thread 1 */                    /* Thread 2 */
while (!flag)                     x = 100;
    ;                             flag = true;
print x;

我們期待印出 100。但 Thread 2 的兩行彼此沒有相依，可能被重排成先 flag = true 再 x = 100，Thread 1 就可能印出 0。

解法是 memory barrier（memory fence）：一道指令，強制在它之前的所有 load 和 store 都完成、並讓其他處理器看得到，才執行之後的指令。在 Thread 2 的兩行中間加 memory_barrier()，就保證 x 先寫入、flag 才設成 true；Thread 1 在 while 之後加，保證先讀 flag 再讀 x。

解法二：硬體指令 test_and_set

硬體提供一個 atomic（不可分割）的指令：讀出舊值並寫入 true，這兩件事中間不可能被打斷。用它就能做出 spinlock：一直嘗試，直到拿到鎖為止。它解決了 Peterson 只能用在兩個 thread、而且怕重排的問題。

缺點是 busy waiting：等的人會一直在迴圈裡空轉，浪費 CPU。在單核 CPU 上更糟，因為拿著鎖的人沒辦法在你空轉時執行。

compare_and_swap 與 Atomic variable

Atomic operation 是指一個操作要嘛完全執行、要嘛完全不執行，不會出現做一半的狀態，像原子一樣不可分割。硬體提供的另一個 atomic 指令是 compare_and_swap（CAS）：如果記憶體裡的值等於預期值，就換成新值；不管有沒有換，都回傳原本的值。

用 CAS 可以做出 atomic variable，例如 atomic 的 increment()：先讀出目前的值，再用 CAS 嘗試把它加一；如果這段時間被別人改過，CAS 會失敗，就重讀再試一次。這樣 count++ 不需要上鎖也不會有 race condition。

單純用 CAS 做的鎖滿足 mutual exclusion，但可能有人一直搶不到。投影片的 bounded-waiting 版本加了 waiting[n] 陣列：離開 critical section 的人依序往後找下一個正在等的 process，直接把它放行（把它的 waiting 設成 false）；找不到才把 lock 解開。這樣任何人最多等 n − 1 輪。

解法三：Mutex lock

一般開發者不會直接用上面那些硬體指令，而是用 OS 提供的高階工具。Mutex lock（mutual exclusion）用一個 boolean 變數 available 表示鎖能不能拿，進 critical section 前 acquire()、出來後 release()。這兩個呼叫本身必須是 atomic，用前面的硬體指令實作。

課本版本的 acquire() 拿不到鎖就一直在迴圈裡等，也就是 busy waiting，這種鎖叫 spinlock（前面的 test_and_set、CAS 鎖都是）。它浪費 CPU，但不用 context switch，省下切換的時間，所以適合 critical section 一次只會被佔用一小段時間的情況，在多核心電腦上被大量使用：核心多，暫時被佔用一兩顆也不怕。

POSIX 提供的是 pthread_mutex_t：用 pthread_mutex_init 建立、pthread_mutex_lock 取得、pthread_mutex_unlock 釋放（見「實際例子」）。

補充

實際函式庫的 mutex 常是混合式：先 spin 一小段時間，還拿不到才讓 thread 去睡（進入 waiting、讓出 CPU）。細節依作業系統和函式庫實作而異。

解法四：Semaphore

Semaphore（號誌、信號、旗號）是一個管控資源的計數器，只能透過兩個不可分割的 atomic 操作去存取：

  • wait()：常叫做 P operation（荷蘭文 proberen，測試）。把計數器減一，如果沒有資源可用，這個 process 或 thread 就要排隊等待。
  • signal()：常叫做 V operation（荷蘭文 verhogen，遞增）。把計數器加一，如果有人在等這個資源，就叫醒其中一個。

可以把它想成停車場入口的空位看板：開進去前先 wait，沒位子就在門口排隊；開出來時 signal，讓排隊的第一台車進去。

Binary semaphore
計數器只會是 0 或 1，管控一個資源，行為和 mutex 類似。
Counting semaphore
計數器可以是任意整數，管控同一種資源的好幾份。

counting semaphore 的計數器（#record）代表的意思：

計數器的值意思
大於 1還有好幾份資源可以用
等於 1剛好剩一份
等於 0缺貨，但沒有人在排隊
小於 0缺貨，而且有人在排隊，負數的絕對值就是排隊的人數

用 semaphore 控制執行順序

semaphore 不只能做互斥，還能排先後順序。假設希望 P1 的 S1 做完之後，P2 才執行 S2：建立一個初始值 0 的 semaphore synch，P1 做完 S1 後 signal(synch)，P2 在 S2 前面 wait(synch)。

  • P2 先跑到 wait：計數器是 0，代表一開始就鎖住，P2 只能等。
  • P1 做完 S1 並 signal：計數器加一，P2 才能往下執行 S2。

Semaphore 的實作

最直覺的寫法是讓 wait() 在計數器小於等於 0 時一直空轉，等到大於 0 才減一，這其實就是 spinlock，會 busy waiting。實際的實作改成 non-busy waiting：semaphore 除了整數 value，還帶一條 PCB list 當作 waiting queue。

  • wait：先把 value 減一，如果變成負數，就把自己加進 list，然後 sleep（進入 waiting、讓出 CPU）。
  • signal：先把 value 加一，如果 value 仍然小於等於 0，代表還有人在等，就從 list 拿出一個 process 並 wakeup。

waiting queue 可以用任何能滿足 bounded waiting 的排隊方式，例如 FIFO，這樣排隊的人就不會永遠搶不到。

wait 和 signal 本身也是共用資料的操作，必須是 atomic。要怎麼保證？

  • 單核心：在 wait 和 signal 執行期間關掉 interrupt。
  • 多核心：關掉所有核心的 interrupt 會嚴重影響效能，所以改用 spinlock 保護 wait 和 signal 這一小段程式，可以用軟體解法，也可以用 test_and_set、CAS 這類硬體指令（實作上也是 busy waiting）。因為 wait 和 signal 的程式很短，佔用的時間很短，用 spinlock 是可以接受的。

用 semaphore 解 n 個 process 的 critical section

所有 process 共用一個初始值 1 的 semaphore sem，進 critical section 前 wait(sem)、出來後 signal(sem)。三個條件都滿足：

  • Mutual exclusion：計數器最多是 1，一次只有一個 process 能進 critical section。
  • Progress：出來的人 signal 之後，critical section 一空出來，waiting list 的第一個就可以進去；出來的人想再進去，要回到 waiting list 重新排隊。
  • Bounded waiting：進入 waiting list 排隊，而且不能插隊。
常見錯誤

semaphore 解起來比較容易，但不保證正確，正不正確全看開發者有沒有把 wait 和 signal 放在對的位置、用對的順序。寫成 signal(mutex) … critical section … wait(mutex) 會讓好幾個人同時進去；寫成 wait(mutex) … critical section … wait(mutex) 會永遠卡住；漏寫其中一個也一樣會出事。

解法五：Monitor

因為 semaphore 太容易用錯，程式語言提供了更高階、模組化的同步工具 Monitor。它很像物件導向語言裡的 class：

  • 裡面有成員變數（共用資料）、操作這些資料的 method，以及初始化用的 constructor。
  • method 只能存取 monitor 自己的成員變數，以及透過參數傳進來的變數。
  • 同一時間只有一個 process 能在 monitor 裡活動，互斥由語言自動處理，開發者不用自己寫 wait 和 signal。

生活例子：monitor 像一間只有一個櫃檯的銀行，所有業務都要到櫃檯辦，櫃檯一次只服務一個人，其他人在門口排隊，不可能兩個人同時改同一本存摺。

Condition variable

monitor 把整個物件鎖住，有時候不夠有效率，也不夠彈性。例如有好幾種不同的條件要等，就需要 condition variable（CV）。宣告 condition x; 之後，x 內部會維護一個 queue，等同於在 monitor 裡多開好幾條 waiting queue，可以自由控制哪個 thread 能進去。

x.wait()
呼叫的 process 被暫停，放進 x 的 queue，直到有別的 process 呼叫 x.signal()。
x.signal()
從 x 的 queue 裡恰好喚醒一個暫停的 process。如果 queue 裡沒有人，signal() 什麼事都不做。
常見錯誤

CV 的 signal 和 semaphore 的 signal 不一樣：semaphore 的 signal 一定會把計數器加一，就算現在沒人在等，之後來的人也用得到這次 signal；CV 的 signal 在沒人等的時候就直接消失，不會被記住。

Signal 之後誰先跑：Hoare 和 Mesa

假設 P 呼叫了 x.signal()，而 Q 正停在 x.wait()。Q 被叫醒之後，P 和 Q 都想在 monitor 裡繼續執行，但 monitor 同時只能有一個 process 活動，所以只能有一個繼續。要馬上讓 Q 跑，還是等 P 做完其他事離開後再讓 Q 跑？有兩種選擇：

Hoare：Signal and wait
P 等 Q。P 發出 signal 之後就暫停，直到 Q 離開 monitor 或去等另一個條件。
Mesa：Signal and continue
Q 等 P。被叫醒的 Q 要等到 P 離開 monitor 或去等另一個條件，才能繼續。

兩種各有優缺點，由程式語言的實作者決定要用哪一種。

Liveness

process 在搶鎖的時候，可能會無限期地等下去，這就違反了 progress 和 bounded waiting。Liveness 指的是系統必須滿足的一組性質，用來確保 process 能持續往下執行。下面兩個是常見的 liveness 問題。

Liveness 問題一：Deadlock

Deadlock（死結）是兩個以上的 process 無限期地等待一個事件，而這個事件只有其中某個正在等的 process 才能觸發。

例子：S 和 Q 是兩個初始值 1 的 semaphore。P0 先 wait(S) 再 wait(Q)，P1 先 wait(Q) 再 wait(S)。

  • P0 拿到 S、P1 拿到 Q，兩個計數器都變成 0。
  • P0 接著 wait(Q)，要等 P1 signal(Q)；P1 接著 wait(S)，要等 P0 signal(S)。
  • 兩個 signal 都永遠不會執行到，形成循環等待（circular wait），P0 和 P1 就 deadlock 了。

Liveness 問題二：Priority inversion

有三個 process L、M、H，優先權 H > M > L。H 需要 semaphore S，但 S 現在被 L 拿著，所以 H 要等 L 用完。這時候 M 變成 runnable，因為 M 比 L 優先，就把 L 搶走了。結果是：

  • L 拿不到 CPU，沒辦法用完 S 再釋放。
  • H 只能繼續等 L，等於被優先權比它低的 M 間接拖住。

高優先權的 process 反而要等低優先權的，這就叫 priority inversion（優先權反轉）。

解法是 priority-inheritance protocol（優先權繼承）：正在使用高優先權 process 所需資源的 process，會暫時繼承那個高優先權，直到用完資源為止。以上面的例子來說，L 暫時繼承 H 的優先權，M 就搶不走 L；L 用完 S 之後放掉繼承來的優先權，H 就能拿到 S。

實際例子

手動追蹤 race condition

counter 一開始是 5，T1 和 T2 各做一次 counter++，正確答案應該是 7。看看下面這種交錯：

時間T1T2counter
1reg1 = counter（5）5
2reg1 = reg1 + 1（6）5
3context switch 到 T25
4reg2 = counter（5）5
5reg2 = reg2 + 1（6）5
6counter = reg26
7counter = reg16

最後是 6 不是 7。問題在 T2 讀到的是 T1 還沒寫回去的舊值。

用 pthread 實際跑一次

#include <stdio.h>
#include <pthread.h>

#define N 1000000

long counter = 0;
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;

void *worker(void *arg) {
    for (int i = 0; i < N; i++) {
        pthread_mutex_lock(&lock);     // 把這行和 unlock 拿掉就會出現 race condition
        counter++;
        pthread_mutex_unlock(&lock);
    }
    return NULL;
}

int main(void) {
    pthread_t t1, t2;
    pthread_create(&t1, NULL, worker, NULL);
    pthread_create(&t2, NULL, worker, NULL);
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
    printf("counter = %ld (expected %d)\n", counter, 2 * N);
    return 0;
}

編譯：gcc race.c -o race -pthread

  • 有加鎖：每次都印 counter = 2000000 (expected 2000000)。
  • 拿掉鎖：多核心電腦上通常會印出小於 2000000 的數字，而且每次跑都不一樣，這就是 race condition 的特徵。

指令重排會讓結果變怎樣？

延續「核心觀念」裡 flag 和 x 的例子，Thread 2 的指令可能有兩種執行順序：

Thread 2 實際執行的順序Thread 1 印出說明
x = 100 → flag = true100照程式順序，正確
flag = true → x = 1000 或 100Thread 1 看到 flag 變 true 時，x 可能還沒寫入，結果看誰先執行，就是 race condition

在 Thread 2 的兩行中間加上 memory barrier 後，只剩第一種順序，一定印出 100。

追蹤 counting semaphore 的計數器

一間自習室有 2 個座位，用初始值 2 的 semaphore S 管控。A、B、C、D 四個人依序來，之後 A、B 離開：

步驟動作S.valueS.list（排隊的人）說明
0初始2空有 2 個座位
1A 呼叫 wait1空A 坐下
2B 呼叫 wait0空B 坐下，座位滿了，但沒人在排隊
3C 呼叫 wait−1C值小於 0，C 進 list 並 sleep
4D 呼叫 wait−2C、D2 個人在排隊，剛好是 −2 的絕對值
5A 呼叫 signal−1D加一後仍小於等於 0，叫醒 C，C 坐下
6B 呼叫 signal0空加一後仍小於等於 0，叫醒 D，D 坐下

注意第 5、6 步：signal 把值加一之後還是小於等於 0，代表有人在等，所以要從 list 叫醒一個人，而不是讓座位空著。

Deadlock 的時間軸

延續「核心觀念」裡 S、Q 的例子，兩個 semaphore 初始值都是 1：

時間P0P1SQ
1wait(S)，拿到 S01
2wait(Q)，拿到 Q00
3wait(Q)，Q 被 P1 拿著，sleep0−1
4wait(S)，S 被 P0 拿著，sleep−1−1

第 4 步之後兩個人都在睡，能叫醒 P0 的只有 P1 的 signal(Q)，能叫醒 P1 的只有 P0 的 signal(S)，誰都等不到，就是 deadlock。如果 P1 也照「先 S 再 Q」的順序拿，第 2 步 P1 就會在 S 上等，P0 可以順利拿到 Q、做完再全部 signal，不會卡住。

1L 拿到 semaphore S，開始用L 拿到 semaphore S，開始用
2H 想要 S，只能等 LH 想要 S，只能等 L；L 暫時繼承 H 的優先權
3M 變成 runnable，比 L 優先，搶走 CPUM 變成 runnable，但 L 現在的優先權比 M 高，M 搶不走
4M 跑完，L 才繼續用 SL 用完 S 並釋放，放掉繼承來的優先權
5L 釋放 S，H 終於拿到H 拿到 S 開始執行，之後才輪到 M

左邊那欄 H 多等了 M 整段執行時間，這段等待跟 H 需要的資源完全無關，就是 priority inversion 的問題所在。

Pseudocode

Peterson's solution（thread i，對方是 j = 1 − i）

// 共用變數
flag[2] = {false, false}
turn = 0

WHILE true
    flag[i] = true            // 我想進去
    turn = j                  // 先禮讓對方
    WHILE flag[j] AND turn == j
        // busy wait：對方想進去而且輪到對方，我就等
    END WHILE

    // ===== critical section =====

    flag[i] = false           // 我出來了
    // remainder section
END WHILE

test_and_set spinlock

// 硬體保證整個函式是 atomic
FUNCTION test_and_set(target)
    old = *target
    *target = true
    RETURN old
END FUNCTION

lock = false

FUNCTION acquire()
    WHILE test_and_set(&lock) == true
        // 拿到的舊值是 true，代表別人拿著鎖，繼續轉
    END WHILE
END FUNCTION

FUNCTION release()
    lock = false
END FUNCTION

強制輪流法（process i，對方是 j）

turn = 0                       // 共用：現在輪到誰

WHILE true
    WHILE turn != i
        // 不是我的回合，一直等
    END WHILE
    // ===== critical section =====
    turn = j                   // 把權利交給對方
    // remainder section
END WHILE

compare_and_swap 與 atomic increment

// 硬體保證整個函式是 atomic
FUNCTION compare_and_swap(value, expected, new_value)
    temp = *value
    IF *value == expected THEN
        *value = new_value
    END IF
    RETURN temp                    // 永遠回傳原本的值
END FUNCTION

// 用 CAS 做 atomic variable 的加一
FUNCTION increment(v)
    DO
        temp = *v
    WHILE temp != compare_and_swap(v, temp, temp + 1)
    // 如果中間被別人改過，CAS 失敗，重讀再試
END FUNCTION

CAS + bounded waiting（n 個 process）

waiting[n] = {false, ...}      // 誰正在等
lock = 0                       // 0 = 沒鎖

WHILE true
    waiting[i] = true
    key = 1
    WHILE waiting[i] AND key == 1
        key = compare_and_swap(&lock, 0, 1)
    END WHILE
    waiting[i] = false
    // ===== critical section =====
    j = (i + 1) % n
    WHILE j != i AND NOT waiting[j]
        j = (j + 1) % n            // 依序找下一個正在等的人
    END WHILE
    IF j == i THEN
        lock = 0                   // 沒人在等，解鎖
    ELSE
        waiting[j] = false         // 直接放行下一個人
    END IF
    // remainder section
END WHILE

Mutex lock（課本的 spinlock 版本）

available = true

FUNCTION acquire()             // 整個函式必須是 atomic
    WHILE NOT available
        // busy waiting
    END WHILE
    available = false
END FUNCTION

FUNCTION release()
    available = true
END FUNCTION

Semaphore 概念版（busy waiting）

// 只示意計數器怎麼控制，實際上就是 spinlock
FUNCTION wait(S)
    WHILE S <= 0
        // busy wait：大於 0 才繼續
    END WHILE
    S = S - 1
END FUNCTION

FUNCTION signal(S)
    S = S + 1
END FUNCTION

Semaphore 實作版（non-busy waiting）

// S.value：整數，負數代表有幾個人在等
// S.list：在等這個 semaphore 的 process（PCB list）
// wait 和 signal 整個都必須是 atomic
FUNCTION wait(S)
    S.value = S.value - 1
    IF S.value < 0 THEN
        S.list.add(current_process)   // 排隊
        sleep()                       // 進入 waiting，讓出 CPU
    END IF
END FUNCTION

FUNCTION signal(S)
    S.value = S.value + 1
    IF S.value <= 0 THEN              // 還有人在等
        p = S.list.remove()
        wakeup(p)                     // 把 p 移回 ready queue
    END IF
END FUNCTION
記憶技巧

S.value 是負數時，它的絕對值剛好等於「正在等的人數」。例如 S.value = −2 代表有兩個 process 在排隊。

n 個 process 的 critical section

semaphore sem = 1              // 所有 process 共用

// Process i
WHILE true
    wait(sem)
    // ===== critical section =====
    signal(sem)
    // remainder section
END WHILE

用 semaphore 排順序（S1 做完才做 S2）

semaphore synch = 0            // 一開始鎖住

// P1
S1
signal(synch)                  // S1 做完才開放

// P2
wait(synch)                    // 等 P1 的 signal
S2

Monitor 的結構

MONITOR monitor_name
    // 成員變數（共用資料），只能被下面的 method 存取
    condition x, y             // condition variable

    FUNCTION p1(...)
        ...
        IF 條件不成立 THEN
            x.wait()           // 暫停，進 x 的 queue
        END IF
        ...
    END FUNCTION

    FUNCTION p2(...)
        ...
        x.signal()             // 叫醒 x queue 裡的一個人，沒人就什麼都不做
    END FUNCTION

    FUNCTION initialization_code(...)
        ...                    // 設定成員變數的初始值
    END FUNCTION
END MONITOR
// 同一時間只有一個 process 能在 monitor 的任何 method 裡執行

比較整理

方法層級等待方式優點缺點適用情境
強制輪流法純軟體busy waiting簡單，有 mutual exclusion缺 progress：沒意願的人佔著權利只用來說明問題
Peterson's solution純軟體busy waiting不需硬體支援，好理解三個條件只能兩個 thread，現代 CPU 上不保證正確教學用
test_and_set spinlock硬體指令busy waiting不用 context switch，鎖很快釋放時最快浪費 CPU，單核上效果差多核心、critical section 很短
compare_and_swap / atomic variable硬體指令失敗就重試不用上鎖就能安全地更新單一變數只適合簡單的更新，例如計數器計數器、做出其他鎖
Mutex lock作業系統課本版本 busy waiting（spinlock），函式庫實作常會睡覺介面簡單，不用接觸硬體指令spin 太久浪費 CPU一般的互斥需求、短的 critical section
Binary semaphore作業系統block和 mutex 類似，也能做順序控制沒有「誰鎖誰解」的擁有者概念，容易用錯互斥、兩個 thread 之間的先後順序
Counting semaphore作業系統block可以管理 N 份資源wait/signal 順序寫錯就 deadlock，難除錯連線池、bounded buffer
Monitor程式語言block（在 entry queue 或 CV 的 queue 等）互斥由語言自動處理，不容易用錯；CV 能精準控制誰等誰醒需要語言支援，signal 之後誰先跑要看實作（Hoare 或 Mesa）Java 的 synchronized、需要好幾種等待條件的情況

兩種 liveness 問題的比較：

問題發生原因結果解法
Deadlock兩個以上的 process 互相等對方手上的資源，形成循環等待大家都永遠等下去例如所有人用同樣的順序拿資源（第 08 章 Deadlocks 會詳細介紹）
Priority inversion高優先權的 H 等低優先權的 L 釋放資源，L 又被中優先權的 M 搶走H 被 M 間接拖住priority-inheritance protocol

自我測驗

Q1. 兩個 thread 只用一個共用變數 turn 嚴格輪流進入 critical section（T0 進完換 T1，T1 進完換 T0），違反了哪個條件？

答案：Progress。

原因：如果現在 turn = 1，但 T1 根本不想進去，T0 想進去卻只能一直等。critical section 明明沒人用，卻不能讓想進去的人進去，就是違反 progress。mutual exclusion 倒是有滿足。

Q2. 一台印表機伺服器有 3 台印表機，要用 semaphore 控制同時使用的人數，初始值要設多少？第 5 個人呼叫 wait 後 S.value 是多少？

答案：初始值 3；第 5 個人呼叫 wait 後 S.value = −2。

原因：counting semaphore 的初始值就是資源數量。每個 wait 減一：3 → 2 → 1 → 0 → −1 → −2。前 3 個人拿到印表機，第 4、5 個人在等，負數的絕對值 2 剛好就是等待人數。

Q3. 為什麼在單核 CPU 上用 spinlock 通常是壞主意？

答案：因為空轉的 thread 佔著唯一的 CPU，拿著鎖的 thread 沒辦法執行去釋放鎖。

原因：spinlock 的前提是「拿著鎖的人正在別的核心上跑，很快就會放開」。單核時拿著鎖的人一定不在跑，等的人只能空轉到自己的 time slice 用完，被切換走之後持有者才有機會執行，完全是浪費。這時候用會讓出 CPU 的 mutex 比較好。

Q4. 為什麼「暫時關掉 interrupt」可以在單核心上保護 kernel 的 next_available_pid，在多核心上卻不行？

答案：關中斷只能讓自己這顆 CPU 不被打斷，其他 CPU 本來就在同時執行，還是能存取同一個變數。

原因：單核心上，別的 process 要執行一定要先透過中斷把 CPU 搶走，關掉中斷就沒人能插進來。多核心上兩個 process 可以真的同時在兩顆 CPU 上跑，根本不需要打斷你，所以要用 CAS 或 mutex 這類能跨核心的同步工具。

Q5. 用 compare_and_swap 實作的 increment() 裡，為什麼要用 do-while 迴圈？

答案：因為讀出舊值和 CAS 之間，別的 thread 可能已經改過這個變數，這時 CAS 會失敗，必須重讀再試。

原因：CAS 只有在「目前的值還等於我剛剛讀到的 temp」時才會寫入 temp + 1，並回傳原本的值。回傳值不等於 temp 代表被別人搶先改了，這次的加一沒有成功，所以用迴圈一直試到成功為止，保證每一次加一都不會被蓋掉。

Q6. 想讓 P2 的 S2 一定在 P1 的 S1 之後執行，semaphore synch 的初始值要設成多少？如果設成 1 會怎樣？

答案：設成 0。設成 1 的話，P2 可能在 S1 還沒做完前就執行 S2。

原因：初始值 0 代表一開始就鎖住，P2 跑到 wait(synch) 時一定要等 P1 做完 S1、呼叫 signal(synch) 才能繼續。如果初始值是 1，P2 一開始 wait 就能把 1 減成 0 直接通過，順序就沒有保證了。

Q7. Monitor 裡的 condition variable 呼叫 x.signal() 時，如果 x 的 queue 沒有人在等，會發生什麼事？這和 semaphore 的 signal 有什麼不同？

答案：什麼事都不會發生。semaphore 的 signal 則一定會把計數器加一。

原因：condition variable 沒有計數器，只有一條 queue，signal 只能叫醒已經在 queue 裡的人，沒人在等就直接消失。semaphore 的 signal 會留下記錄，之後才來 wait 的人可以直接用掉這次 signal，不用等待。

Q8. P 在 monitor 裡呼叫 x.signal() 叫醒了 Q。在 Hoare 和 Mesa 兩種做法下，接下來分別是誰在執行？

答案：Hoare（signal and wait）是 Q 先執行，P 等待；Mesa（signal and continue）是 P 繼續執行，Q 等待。

原因：monitor 同一時間只能有一個 process 活動，P 和 Q 只能有一個繼續。Hoare 讓被叫醒的 Q 馬上執行，P 要等 Q 離開 monitor 或去等另一個條件；Mesa 讓 P 做完自己的事，Q 要等 P 離開或去等另一個條件。

Q9. 優先權 H > M > L，L 拿著 H 需要的 semaphore 時，M 變成 runnable。為什麼說 H 被「反轉」了？priority inheritance 怎麼解決？

答案：因為 M 搶走 L 的 CPU，L 沒辦法釋放資源，H 就變成要等比自己低優先權的 M 跑完。priority inheritance 讓 L 暫時繼承 H 的優先權，M 就搶不走 L。

原因：H 本來只需要等 L 用完資源，但 M 的出現讓 L 停下來，H 的等待時間多了一整段 M 的執行時間，而 M 根本不需要這個資源。L 繼承 H 的優先權後會比 M 優先，可以盡快用完並釋放 S，之後再放掉繼承來的優先權，H 就能接著執行。
